# HT-089: Session Ownership Contract Alignment

**Status:** Draft
**MoSCoW:** Must
**Kano:** Basic
**Phase:** 1 (Hometower)
**Size:** M

## Job-to-be-Done

As a Hometower maintainer, I want one enforceable contract for SQLModel session ownership and transaction boundaries so that architecture checks, code reviews, and future refactors can distinguish valid service orchestration from real layer leaks.

## Context

Hometower's current architecture contract is internally inconsistent. [AGENTS.md](/Users/jayharry28/Projects/hometower/AGENTS.md) states that `src/repositories/` is the only layer with SQLModel `Session`, while also stating that `src/services/` owns `session.commit()`. In practice, the codebase currently passes `Session` through many service functions and some API startup/runtime paths.

This mismatch surfaced during review as a repo-wide `Session` containment failure that could not be trusted as a useful signal. The underlying problem is not just grep noise. Hometower currently lacks one explicit, enforceable transaction-boundary rule that covers:

- where `Session` may appear in type signatures
- which layer may create, pass, commit, rollback, or close it
- how review and gate tooling should detect real violations

Until this contract is aligned, future reviews can produce false failures or, worse, miss genuine layer leaks.

## Acceptance Criteria

Feature: Session ownership contract is explicit and enforceable

Scenario: Architecture contract defines one allowed session-boundary model
Given Hometower's layered architecture is documented in AGENTS and local skills
When an engineer reads the session-boundary rules
Then the documentation states exactly which layers may reference SQLModel `Session`
And it states which layer owns transaction lifecycle actions (`commit`, `rollback`, `close`)
And it does not contain conflicting instructions about repository-only session ownership versus service-owned commits.

Scenario: Review and gate tooling align with the documented contract
Given the approved session-boundary contract has been chosen
When the architecture enforcement commands and code-review checks run
Then valid baseline usage does not trigger false positives
And real violations in disallowed layers still fail the review or gate
And the enforcement path is documented as part of the repo's standard verification flow.

Scenario: Existing baseline code follows the chosen contract
Given the codebase contains existing service and startup paths that reference `Session`
When the implementation for this story is complete
Then those paths are either refactored to the approved boundary model or explicitly allowed by the updated contract
And there is no remaining repo-wide ambiguity about whether current usage is compliant.

Scenario: New contributors can extend transaction-aware features safely
Given an engineer adds a new service or route that touches the database
When they follow the documented coding patterns
Then they can determine where `Session` should be created and passed without guessing
And Code-Reviewer can approve or reject the change based on one unambiguous rule.

## Non-Goals (explicitly out of scope)

- Rewriting all repository, service, and router patterns unrelated to session ownership in one bulk refactor.
- Changing user-facing behavior in topology, inventory, or settings flows unless required by the chosen transaction-boundary contract.
- Replacing SQLModel or introducing unrelated infrastructure changes.

## Business Invariants

- Hometower must have exactly one authoritative rule for SQLModel `Session` ownership and transaction boundaries.
- Transaction commits and rollbacks must remain deliberate and predictable; no feature may create ambiguous cross-layer transaction control.
- Domain code remains pure and never imports SQLModel, FastAPI, or Loguru.
- UI code never imports repositories directly, regardless of the chosen session-boundary model.

## Resolved Contract (21 Apr 2026)

- Routers may inject a request-scoped `Session` via `Depends(get_session)` and pass it to services.
- Services may accept `Session` and own `commit()` / `rollback()` for application workflows.
- Repositories may accept `Session`, perform query/mutation/flush/refresh/delete mechanics, and never `commit()` / `rollback()`.
- `Session` creation is limited to approved infrastructure entry points such as `src/utils/db.py`, `src/api/app.py`, and `src/api/middleware/auth.py` unless Architect explicitly approves another path.
- CI/static enforcement should reject unauthorized `Session` creation and router-owned transaction control instead of flagging every service/router signature that references `Session`.

## Notes for Architect / Engineer

- This story exists because the current repo guidance is self-contradictory, not because one isolated file is wrong.
- The approved model preserves service-layer `Session` parameters and request-scoped router injection; the work is contract alignment plus enforcement clarity, not a repo-wide repository-only refactor.
- AGENTS, coding patterns, review tooling, and CI-Gatekeeper must be updated together so the rule becomes explicit and testable.
- A narrow cleanup remains for any router that still owns `commit()` / `rollback()` directly; those paths should move transaction control into the service layer.
