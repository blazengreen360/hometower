# HT-021: Device Containers (Nested Logical/Physical Grouping)

**Status:** Ready
**MoSCoW:** Must
**Kano:** Performance — every additional nesting level makes the topology more accurately represent real infrastructure. Homelabbers think in containment hierarchies (host → VM → container → service). Without this, the inventory is flat and misleading.
**Phase:** 1 (Hometower)
**Size:** L (5-6 days)

## Job-to-be-Done
As a homelab owner, I want any device to act as a container for other devices so that my topology diagram mirrors reality — a Proxmox host holds VMs, a Docker host holds containers, a rack holds servers — without resorting to naming conventions or notes.

## Context
Real homelab infrastructure is deeply hierarchical. A physical server runs Proxmox, which hosts VMs, which run Docker, which runs containers, which expose services. Today, Hometower's topology canvas treats every device as a peer — a flat graph of nodes and edges. That doesn't match how homelabbers think or how infrastructure actually works.

This story makes containment a first-class concept. Any existing device can be "promoted" to a container. Once promoted, other devices can be placed inside it. On the canvas, containers render as Cytoscape.js compound nodes — visually nested boxes that expand/collapse. In the data model, it's a self-referential `parent_id` on Device.

Key design decision: **containment is a property of any device, not a separate entity type.** A server doesn't stop being a device when it becomes a container. It retains its type, IP, MAC, tags — it just also has children. This avoids a parallel model and keeps the single-Device inventory intact.

Example topology:
```
Rack-01 (container)
├── pve-01 (Server, container)
│   ├── docker-host-vm (VM, container)
│   │   ├── pihole (Container)
│   │   ├── traefik (Container)
│   │   └── nextcloud (Container)
│   └── home-assistant-vm (VM)
├── truenas-01 (NAS)
└── unifi-switch (Switch)
```

## Acceptance Criteria

### Data model
- Given a device exists, when I inspect the Device model, then it has an optional `parent_id` field (nullable self-referential FK to `devices.id`)
- Given I set a device's `parent_id` to another device's ID, when I save, then the child device is persisted with that parent relationship
- Given I try to set a device's `parent_id` to its own ID, when I save, then the API returns HTTP 400 ("Device cannot be its own parent")
- Given device A is inside device B which is inside device C, when I try to set C's `parent_id` to A, then the API returns HTTP 400 ("Circular containment detected") — no cycles allowed

### API
- Given I `POST /api/devices/` with a `parent_id` field, when the parent device exists, then the child device is created with that parent
- Given I `PATCH /api/devices/{id}` with `parent_id` set to a valid device ID, when the request completes, then the device is re-parented (moved into the container)
- Given I `PATCH /api/devices/{id}` with `parent_id` set to `null`, when the request completes, then the device becomes top-level (removed from container)
- Given I `GET /api/devices/{id}?include=children`, when the device has children, then the response includes a `children` array of child device summaries
- Given I `GET /api/devices/` list endpoint, when devices have parents, then each device response includes `parent_id` (the list remains flat — tree-building is client-side)
- Given I `DELETE /api/devices/{id}` on a device that has children, when the request fires, then it returns HTTP 400 ("Device has child devices — remove or reassign them first")

### Canvas (Cytoscape.js compound nodes)
- Given a device has children in the database, when the topology canvas loads, then the parent renders as a Cytoscape compound node with children visually nested inside it
- Given I right-click a device on the canvas, when I select "Convert to Container", then the device visually expands to a compound node bounding box (even with zero children)
- Given a device is a container, when I drag another device into it on the canvas, then the dropped device's `parent_id` is set via `PATCH` and it renders inside the container
- Given a child device is inside a container, when I drag it out of the container bounds, then its `parent_id` is cleared via `PATCH` and it becomes top-level
- Given a container has children, when I click the collapse toggle, then the container shrinks to its device icon with a badge showing child count (e.g. "3")
- Given a container is collapsed, when I click the expand toggle, then the container opens to show all children with their positions
- Given a collapsed container has connections to its children, when I view the canvas, then the connections visually route to the collapsed parent node
- Given a container is expanded, when I view connections, then each child's connections render to/from the child node directly

### Device detail panel
- Given I select a container device, when the detail panel opens, then it shows a "Children" section listing contained devices with their type icons
- Given I select a child device, when the detail panel opens, then it shows a "Parent" breadcrumb (e.g. "Inside: pve-01 → Rack-01") that is clickable to select the parent

### Nesting
- Given multi-level nesting (A contains B contains C contains D), when the canvas renders, then all levels are visually nested (Cytoscape supports arbitrary compound depth)
- Given a deeply nested device, when I view it in the detail panel, then the full parent chain is shown as a breadcrumb

## Non-Goals (explicitly out of scope)
- Automatic child discovery (Proxmox API → auto-populate VMs) — that's Phase 2 (LT-001, LT-002)
- Container "templates" (pre-built hierarchies like "standard Proxmox host") — possible future Delighter
- Restricting which DeviceTypes can contain which (e.g., "only Servers can contain VMs") — v1 allows any device to contain any device, type-aware rules are a refinement
- Drag-to-reorder children within a container — children are freely positioned on the canvas
- Container-level aggregate stats (total RAM, CPU across children) — future Delighter
- Connections between containers at the group level ("site-to-site link") — connections remain device-to-device

## Open Questions
None — the data model approach (`parent_id` self-referential FK + Cytoscape compound nodes) is confirmed. The Architect should decide on cycle-detection strategy (recursive CTE vs. depth limit) in the RFC.

## Notes for Architect / Engineer

### Data model
- Add `parent_id: uuid.UUID | None = None` to Device as a nullable FK to `devices.id` with `ON DELETE RESTRICT`
- Alembic migration adds the column + FK + index on `parent_id`
- Domain layer: `validate_no_cycle(device_id, new_parent_id, session)` — walk up the parent chain (recursive CTE or iterative query) to detect cycles. Cap at a reasonable depth (e.g. 10 levels) as a safety net
- Domain layer: `validate_not_self_parent(device_id, parent_id)` — trivial check

### Canvas (Cytoscape.js)
- Cytoscape.js compound nodes: set `data.parent` on a node element to nest it inside another node — this is native Cytoscape behavior, no plugin needed
- Collapse/expand: use the `cytoscape-expand-collapse` extension (CDN) or implement manually with show/hide + badge
- Drag-reparent: listen to `node.position` events — if a node is dropped inside another node's bounding box, fire `PATCH` with `parent_id`. If dropped outside, clear `parent_id`
- Container visual: compound nodes auto-size to fit children. Style with a distinct border/background (e.g. dashed border, translucent fill matching DeviceType color)
- Collapsed state: replace compound with a regular node showing the device icon + child count badge. Store collapse state in DiagramLayout's `cytoscape_json`

### Performance
- The `include=children` query param should use a single query with a join, not N+1
- Cycle detection on every re-parent operation is O(depth) — with a max depth cap of 10, this is constant time
- Canvas rendering of deeply nested compounds is handled natively by Cytoscape — no special optimization needed

### RBAC
- Only Contributors and Admins can set/change `parent_id` (same as device edit)
- Readers see the nested canvas view but cannot modify containment

### Migration safety
- Adding a nullable `parent_id` column is backward-compatible — existing devices get `NULL` (top-level)
- No data migration needed — all existing devices remain top-level
