# HT-044: Power Usage Tracking

**Status:** Done
**MoSCoW:** Should
**Kano:** Performance — homelabbers constantly track power draw for UPS sizing, circuit planning, and electricity cost awareness. Reddit threads about homelab power consumption are perennial. NetBox has power distribution modeling; we offer a simpler, homelab-friendly version focused on watts and aggregation.
**Phase:** 1 (Hometower)
**Size:** M (2–3 days)

## Job-to-be-Done
As a homelab owner, I want to record how many watts each device draws so that I can see the total power consumption of a rack, a location, a room, or my entire setup — helping me size UPS units, plan circuits, and understand my electricity costs.

## Context
Power management is a top concern for homelabbers:
- "What's the total draw of Rack A? Will my 1500VA UPS handle it?"
- "How much does my homelab cost me per month in electricity?"
- "If I add two more nodes, do I need a bigger breaker?"

This story adds a `power_watts` field to devices and computes aggregated totals at the location, rack, and global level.

### Scope
- **Per-device**: Manual entry of rated / measured wattage (not auto-detected)
- **Aggregation**: Sum power across devices grouped by location, by parent location, or all devices
- **Cost estimate**: User sets an electricity rate (cost per kWh) in settings; system shows estimated monthly cost

## Acceptance Criteria

### Data model
- Given the migration runs, when I inspect the `devices` table, then a `power_watts` column exists, type `INTEGER`, nullable, default `NULL`
- Given I create a device with `"power_watts": 65`, when it saves, then the value is stored
- Given I create a device without specifying power, when it saves, then `power_watts` = `NULL` (unknown)
- Given existing devices before the migration, when the migration runs, then `power_watts` = `NULL` for all

### Device detail panel
- Given I open a device's detail panel (HT-010), when I view the fields, then a "Power (W)" field is shown as a numeric input
- Given I enter `150`, when I save, then `power_watts` = `150`
- Given I clear the field, when I save, then `power_watts` = `NULL` (unknown/unset)
- Given I enter a negative number or non-numeric value, when I try to save, then validation rejects it

### API
- Given I `POST /api/devices` with `"power_watts": 350`, when the request is valid, then the device is created with that value
- Given I `PATCH /api/devices/{id}` with `"power_watts": null`, when the request succeeds, then the power value is cleared

### Aggregation endpoint
- Given devices exist with `power_watts` values, when I call `GET /api/power/summary`, then the response returns:
```json
{
  "total_watts": 1250,
  "total_devices": 15,
  "devices_with_power": 12,
  "devices_without_power": 3,
  "estimated_monthly_kwh": 900.0,
  "estimated_monthly_cost": 108.00,
  "currency": "USD",
  "cost_per_kwh": 0.12,
  "by_location": [
    {
      "location_id": "uuid",
      "location_name": "Server Rack A",
      "total_watts": 750,
      "device_count": 6,
      "estimated_monthly_cost": 64.80
    }
  ]
}
```
- Given some devices have `power_watts = NULL`, when the summary calculates, then those devices are excluded from watt totals but counted in `devices_without_power`
- Given no electricity rate is configured, when the summary calculates, then `estimated_monthly_cost` and `cost_per_kwh` are `null`

### Electricity rate setting
- Given I am an Admin, when I navigate to Settings, then I see "Electricity Rate" with fields: cost per kWh (numeric, e.g. `0.12`) and currency code (e.g. `USD`, `EUR`, `GBP`)
- Given I set the rate to `0.15 EUR`, when I save, then the power summary uses this rate for cost calculations
- Given the rate is stored, when any user views power data, then cost estimates use the configured rate

### Formula
- Monthly kWh = `total_watts × 24 hours × 30.44 days / 1000`
- Monthly cost = `monthly_kwh × cost_per_kwh`

### Dashboard integration (after HT-026)
- Given HT-026 (app shell) is shipped, when the dashboard renders, then a "Power Usage" card shows: total watts, estimated monthly cost, and a mini bar chart of watts by location
- Given HT-026 is NOT shipped, when the feature is available, then power data is only accessible via the API and the device detail panel

### Inventory list
- Given I view the inventory table (HT-009), when the table renders, then an optional "Power (W)" column is available (hidden by default, toggled via column settings if available)

### Location detail
- Given I view a location's detail (HT-005), when the location has devices with power values, then it shows: "Total power: {sum}W ({count} devices)" at the top of the device list
- Given a location has child locations, when I view the parent, then the total includes devices in child locations (recursive sum)

## Non-Goals (explicitly out of scope)
- Real-time power monitoring (smart plug APIs, SNMP PDU data) — Phase 2 auto-discovery
- Power history / time-series tracking — v1 is a current-state snapshot
- UPS capacity modeling (runtime calculations, battery health)
- PDU / outlet-level tracking (which outlet a device is plugged into)
- Power redundancy / dual-PSU modeling
- Alerts when power exceeds threshold

## Notes for Architect / Engineer
- **Migration**: New Alembic migration adding `power_watts INTEGER` (nullable) to `devices` table.
- **Model update**: Add `power_watts: Optional[int] = Field(default=None, ge=0)` to `DeviceBase`. The `ge=0` Pydantic constraint prevents negative values.
- **Settings storage**: Electricity rate needs a simple key-value settings table or could be stored in an env var. Recommend a new `SystemSettings` model/table with `key VARCHAR PRIMARY KEY, value VARCHAR`. Keys: `electricity_rate_per_kwh`, `electricity_currency`. Only Admin can write.
- **Power summary service**: `src/services/power_service.py` — queries devices with `power_watts IS NOT NULL`, groups by `location_id`, sums. Pure aggregation, no domain complexity.
- **API router**: `src/api/routers/power.py` — `GET /api/power/summary`. Requires authenticated user (any role can read).
- **Recursive location sum**: Use the `parent_id` hierarchy in the Location model. Either a recursive CTE in SQL or an in-memory tree walk (device count is small enough for the latter in a homelab context).
