# HT-005: Location Management (Rack + Geographic)

**Status:** Done
**MoSCoW:** Must
**Kano:** Basic for rack locations, Performance for geo locations
**Phase:** 1 (Hometower)
**Size:** M (3-4 days)

## Job-to-be-Done
As a homelab owner, I want to record where each device physically lives — which rack/row in my garage, or which geographic site for distributed nodes — so that I can find hardware when I need to touch it.

## Context
HT-002 already references `location_id` on Device as a nullable foreign key. This story creates the Location entity and the minimum CRUD so users can start associating devices with places. The `LocationType` enum already exists: `rack`, `geo`.

A location is either:
- **rack** — has `name`, `rack`, `row`, optional `parent_id` for nested hierarchy (e.g. "Garage" > "Rack-A" > "Row 2")
- **geo** — has `name`, `lat`, `lng` for map view rendering (HT-008 consumes this)

This story covers backend + a minimal admin UI (table + create/edit modal) under Settings. The map view is a separate story (HT-008).

## Acceptance Criteria
- Given I am a Contributor, when I `POST /api/locations` with `{name, type: "rack", rack: "A", row: "2", parent_id: null}`, then a rack location is created
- Given I am a Contributor, when I `POST /api/locations` with `{name: "Lisbon DC", type: "geo", lat: 38.7223, lng: -9.1393}`, then a geo location is created
- Given I `POST /api/locations` with `type: "geo"` but no `lat`/`lng`, then I receive a 400 error: "Geographic locations require lat and lng"
- Given I `POST /api/locations` with `type: "rack"` but provide `lat`/`lng`, then I receive a 400 error: "Rack locations must not have coordinates"
- Given I `POST /api/locations` with `lat: 95` (out of range), then I receive a 400 error: "lat must be between -90 and 90"
- Given a parent rack location exists, when I `POST /api/locations` with `parent_id` pointing at it, then the child is created and its parent chain is resolvable via `GET /api/locations/{id}?include=ancestors`
- Given I try to set `parent_id` to a location that would create a cycle (A → B → A), then I receive a 400 error: "Cycle detected in location hierarchy"
- Given a location has devices assigned to it, when I `DELETE /api/locations/{id}`, then I receive a 400 error listing the affected devices
- Given I `GET /api/locations?type=geo`, then I receive only geographic locations (feeds the map view in HT-008)
- Given I am on the Settings → Locations page, when I click "Add Location", then a modal opens with a type toggle (rack | geo) that swaps the visible fields

## Non-Goals (explicitly out of scope)
- Rack visualisation (1U/2U slot diagrams) — not in v1
- Location photos or floor plans
- Auto-geocoding addresses to lat/lng (user enters coordinates directly in v1)
- Multi-tenant location scoping (Phase 2 / LightTower)
- Per-location permissions (v1 uses global RBAC only)

## Open Questions
None — `LocationType` enum is frozen and the parent-chain + cycle rules are fully specified.

## Notes for Architect / Engineer
- SQLModel at `src/models/location.py`: `id`, `name`, `type` (LocationType), `lat` (Optional[float]), `lng` (Optional[float]), `rack` (Optional[str]), `row` (Optional[str]), `parent_id` (Optional[FK self]), `created_at`, `updated_at`
- Pydantic validators: type-dependent field requirements live in domain, not the model — use a domain pure function `validate_location(payload) -> ValidatedLocation` in `src/domain/inventory.py` (or new `src/domain/locations.py` if that file crosses the 250-line cap)
- Cycle detection: pure function `detect_cycle(location_id, new_parent_id, all_locations)` in `src/domain/locations.py`
- Repository at `src/repositories/location_repository.py` — methods: `create`, `get_by_id`, `get_all(type=None)`, `get_ancestors`, `get_devices_at_location`, `update`, `delete`
- Service at `src/services/location_service.py` — enforces the delete-blocks-if-devices-present rule
- Router at `src/api/routers/locations.py` — Pydantic `LocationCreate`, `LocationRead`, `LocationReadWithAncestors`
- Settings page at `src/ui/pages/settings_locations.py` — simple NiceGUI table + modal; follows UX-Designer spec (monospace for numeric coordinates, floating labels, inline validation)
- Alembic migration creating `locations` table; foreign key on `parent_id` with `ON DELETE RESTRICT`
- RBAC: create/update/delete require `Role.Contributor` or higher; read is available to all authenticated users
- `lat`/`lng` stored as `Float` (not Decimal) — map precision of ~11cm is sufficient for homelab use
