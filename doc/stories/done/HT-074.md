# HT-074: Leave-Page Protection for Unsaved Topology Changes

**Status:** Ready
**MoSCoW:** Must
**Kano:** Basic — users should never be forced to guess whether leaving a topology will save, discard, or silently strand their work.
**Phase:** 1 (Hometower)
**Size:** S (1-2 days)

## Job-to-be-Done
As a Contributor, I want a clear choice when leaving a topology with unsaved changes so that I can intentionally save a version, discard my draft, or stay on the page.

## Context
The 14 April 2026 design session settled the leave flow explicitly:

- **Save Version**
- **Discard**
- **Cancel**

This exists because personal drafts and saved history serve different jobs. Drafts protect work in progress. History records intentional checkpoints. Leaving the page must not collapse those two meanings into silent magic.

## Acceptance Criteria
- Given I have unsaved topology changes relative to the latest saved version, when I try to navigate away, close the page, or switch to another route, then I am prompted with `Save Version`, `Discard`, and `Cancel`
- Given I choose **Save Version**, when the save succeeds, then a new history version is created and the pending navigation proceeds
- Given I choose **Discard**, when I confirm, then my current unsaved draft changes are discarded and the pending navigation proceeds
- Given I choose **Cancel**, when I dismiss the prompt, then I remain on the topology page with my draft still intact
- Given no unsaved topology changes exist, when I leave the page, then no prompt appears
- Given the page is being closed via browser/tab close where custom dialogs are constrained, when unsaved changes exist, then the user still receives a browser-native leave warning rather than silent exit

## Non-Goals (explicitly out of scope)
- Multi-step restore or undo flows inside the leave dialog
- Choosing between multiple saved versions from the leave prompt
- Broader navigation redesign outside the topology editor

## Open Questions
None.

## UX Interaction Spec
- **Placement:** a centered confirmation modal for in-app navigation; browser-native fallback for tab close / hard unload.
- **Interaction triggers:** route change, breadcrumb click, sidebar navigation, browser back, or tab close while unsaved changes exist.
- **State transitions:** editing -> leave attempt -> modal shown -> `Save Version` saving state or `Discard` confirmation -> navigate away, or `Cancel` returns to editing.
- **Edge-case constraints:** if save fails, the user stays on the topology page and sees the failure; if no unsaved changes exist, the modal never appears.
- **Fitts's Law justification:** `Save Version` is the primary action and should be the largest button because it is the safest default. `Discard` must be visually separated to require deliberate aim. `Cancel` should be easy to hit because backing out of a risky leave attempt is a common recovery action.

## Notes for Architect / Engineer
- This story depends on the draft/history split from HT-072 and HT-073.
- The prompt logic should compare the current working state against the latest saved history version, not merely whether autosave recently ran.
- Browser `beforeunload` limitations are acceptable; use native warning there and the full 3-choice modal for internal navigation where custom UI is possible.
