# HT-082: Dashboard Revamp & Power Widgets

**Status:** Done
**Shipped:** 18 Apr 2026
**MoSCoW:** Must
**Kano:** Performance — a dashboard without life is a wasted landing page; an informative, high-utility view pulls users in immediately.
**Phase:** 1 (Hometower)
**Size:** L

## Job-to-be-Done

As a homelabber starting a session, I want the dashboard to instantly show me an informative, balanced overview containing my power consumption, inventory counts, and recent changes so that I know what state my lab is in without clicking through multiple pages.

## Context

The current dashboard lacks life, displaying unstructured or unhelpful data. 

Design decision resolved in session: **Balanced Overview**. The dashboard should split focus between:
- High-level inventory statistics (Device types count, Online/Offline status)
- Power consumption visibility (Total and selectable per-workspace)
- Recent activity/history (Changes to topology)

## Acceptance Criteria

Feature: Meaningful Dashboard Overview

  Scenario: Dashboard renders Balanced widgets
    Given a user navigates to the root `/` (Dashboard) page
    When the dashboard loads
    Then it displays a modern grid of metric "cards" (e.g., Total Devices, Total Power Draw, Workspaces, Recent Edits)
    And these cards use the new premiumized UI tokens (HT-080)
    And real data from the database is pulled directly into these metrics

  Scenario: Power Usage metric card
    Given the dashboard is loaded with a Power Usage widget
    When the user views the power widget
    Then it displays the sum of the power draw of all devices in the system
    And it provides a dropdown or segmented control to switch the view from "All" to a specific workspace
    And filtering by workspace dynamically updates the total without a full page reload

  Scenario: Status and Inventory breakdown
    Given the dashboard includes an Inventory breakdown
    When the page renders
    Then the user sees a quick summary of device health (e.g., "Active", "Offline") and counts by type ("Servers: 5", "Switches: 2")
    And clicking a type or status navigates to the pre-filtered `/inventory` page

  Scenario: Recent Activity feed
    Given the user has made edits to topologies or devices
    When viewing the dashboard
    Then a compact "Recent Activity" list shows the last 5 relevant changes (e.g., "Topology updated at HH:MM", "Device X added")
    And clicking an entry links directly to that resource

## Non-Goals (explicitly out of scope)

- Live hardware metrics (CPU/RAM telemetry from agents). This application tracks intent and documentation, not real-time Prometheus/Grafana hardware scraping.
- Customizable or draggable dashboard layouts. A fixed, responsive grid of useful widgets is preferred for phase 1.

## Business Invariants

- The data must be scoped accurately to the user’s role (Readers can see the dashboard, but cannot initiate edits from it).
- Aggregate database queries for the dashboard (like "sum of power") should be handled in `src/repositories/` efficiently without pulling all device rows into memory.

## UX Interaction Spec

- **Layout Structure**: 
    - Top row: 3-4 Key Metric Cards (Total Devices, Power Usage, Offline Alerts, Recent Drafts).
    - Middle row: Split view. Left side: Inventory Types (`echarts` or simple bar/list). Right side: Recent Activity Feed.
- **Power Widget Filter**: Use `ui.select` (dense, outlined) in the top-right corner of the Power card.
- **Fitts's Law**: 
    - Make entire metric cards clickable if they lead to an expansion view (e.g., power details or inventory lists).
- **Responsive**: Switch from 3-4 columns to 1-2 columns on mobile.

## Notes for Architect / Engineer

- Use `src/ui/components/` aggressively to separate the logic of each dashboard widget.
- Build a new `DashboardService` or aggregate endpoint in the FastAPI backend that returns a single `DashboardSummaryResponse`. Executing 5 different round-trips from the NiceGUI page load will induce UI stuttering.
- The recent activity list might require a new minimal historical model or joining `TopologyHistory` + `Device` creation tags. Decide the simplest subset in the RFC.
- If eCharts (`ui.echart`) is used for the inventory breakdown, ensure to format the colors using the standard `--ht-*` CSS variables passed through `run_javascript`.
