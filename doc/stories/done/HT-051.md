# HT-051: Diagram-first device creation — type palette, on-drop form, draft state, Publish

**Status:** Ready
**MoSCoW:** Must
**Kano:** Basic — the canvas is the primary creation surface; without this, users must pre-create every device in inventory before they can draw anything, which is backwards and defeats the purpose
**Phase:** 1 (Hometower)

## Job-to-be-Done
As a homelab author, I want to drag a device type onto my canvas and fill in its details there so that my diagram drives my inventory — I draw first, the inventory is the output, not the prerequisite.

## Context
Currently devices must be created via the inventory form before they appear on a canvas. This is inventory-first. The intended model is **diagram-first**: a device type palette lives in the left panel (alongside the inventory stencil, HT-049); users drag a typed icon (Server, Switch, VM, etc.) onto the View canvas; an inline form collects device details; the node appears in **draft state** on canvas; autosave persists draft devices to the View's `cytoscape_json` but does NOT write to the global inventory; an explicit **"Publish"** action on each draft device individually commits it to the global device inventory.

For already-published devices, edits made via the canvas detail panel (name, IP, notes) propagate to inventory immediately. Removing a published device from the canvas removes it from *this View only* — the device and its global inventory record are unaffected. Un-publishing a device (reverting to draft) is not supported — once published, permanent.

## Acceptance Criteria

**Type palette:**
- Given the View Designer is in edit mode, then a device type palette is visible in the left panel, showing icons for each `DeviceType` (Server, Workstation, Switch, Router, VM, Container, Service, Storage, Other).
- Given the user drags a type icon and drops it onto the canvas, then a device creation form opens immediately (modal or inline popover): fields are Name (required), IP (optional), MAC (optional), OS (optional), Notes (optional). Type is pre-filled from the dragged icon and editable.
- Given the user submits the form, then a node appears on canvas at the drop position in **draft state** (visually distinct: dashed outline, muted colour, a "Draft" badge).
- Given the user dismisses the form without submitting, then no node is added to the canvas.

**Draft state:**
- Given a draft device exists on the canvas, when the canvas autosaves, then the draft device's data (name, type, all form fields) is persisted inside the View's `cytoscape_json` under element data — it is NOT written to the `devices` table.
- Given the user reloads the page, then draft devices are restored from `cytoscape_json` and appear with their draft visual indicator.
- Given a draft device is selected, when the user opens its detail panel, then they can edit all fields; changes persist to the draft in `cytoscape_json` on autosave.
- Given a draft device node is right-clicked and "Delete Draft" is selected, then a confirmation dialog appears: "Delete draft [name]? This cannot be undone."
- Given the user confirms draft deletion, then the draft node and any local-only connections attached to it are removed from `cytoscape_json`. No inventory record exists, so nothing is orphaned.

**Publish to Inventory (per device):**
- Given a draft device is selected (or right-clicked), then a "Publish" action is available — in the detail panel as a prominent button, and in the right-click context menu.
- Given the user clicks "Publish" on a single draft device, then that device is created in the global `devices` table; the draft visual indicator is removed; the node's element ID is updated to the server-assigned UUID.
- Given the Publish action succeeds, then a brief success toast confirms "Device published to inventory".
- Given the Publish action fails (e.g. name conflict), then an error is shown on that node; the device remains in draft state; other drafts are unaffected.
- Given already-published devices have their name/IP/notes edited via the detail panel, then the edit is committed to global inventory immediately on field save (not deferred to Publish).
- Given a toolbar counter shows "{N} drafts" when draft devices exist on canvas, then it serves as a reminder but is NOT a batch-publish trigger.

**Remove published device from View:**
- Given a published device node is right-clicked in edit mode, then the context menu shows "Remove from View".
- Given the user clicks "Remove from View", then a confirmation dialog appears: "Remove [name] from this View? The device stays in your inventory."
- Given the user confirms, then the published device node and all its connections on this View are removed from the canvas and `cytoscape_json`. The device remains in the global inventory, untouched.
- Given the removal is confirmed, then the action is added to the undo stack (HT-032) — undo restores the node and its connections on this View.
- The Delete key does NOT trigger "Remove from View" for published devices — right-click only prevents accidental removal.

**Connections with draft endpoints:**
- Given a draft device and a published device are both on the canvas, when the user draws a connection between them, then the connection is stored in the View's `cytoscape_json` only (local-only, no API call).
- Given a draft device is published and all endpoints of a local-only connection are now published, then the connection is also created via `POST /api/connections/` as part of the Publish action.
- Given a connection has mixed endpoints (one draft, one published), then the connection stays local-only until both endpoints are published.
- Given a connection exists between two draft devices, then publishing one draft does NOT create the connection — both must be published first.

**Interaction:**
- Given the user is in edit mode and clicks "Stop Editing" with draft devices present, then a prompt appears: "You have {N} unpublished draft device(s). They will remain as drafts on this View. Continue?" Consistent with HT-048.

## Non-Goals (explicitly out of scope)
- Does not replace the existing inventory "Add Device" form in the Inventory section — that form remains for inventory-first workflows.
- Does not support batch import from the type palette (one device per drag).
- Does not validate IP uniqueness client-side (server rejects on Publish if duplicate).
- Does not auto-detect device type from MAC OUI (a future Delighter).
- Draft state is per-View — a draft device on View A is not visible in View B until Published.
- **No un-publish.** Once a device is published to global inventory, it cannot be reverted to draft state. The user can remove it from Views or delete it from inventory (HT-052), but not un-publish.
- Does not cover complete device deletion from global inventory — see HT-052.

## UX Interaction Spec
**Left panel layout (edit mode):**
```
┌─────────────────────┐
│ [Type Palette]      │  ← top half: draggable type icons in a grid (3 per row)
│  🖥 Server  🔀 Switch │
│  🖧 Router  💻 VM    │
│  📦 Contain 🛠 Svc  │
├─────────────────────┤
│ [Inventory Stencil] │  ← bottom half: published devices (HT-049), collapsible
│  Search…            │
│  ○ my-server  …     │
└─────────────────────┘
```
- Panel is 260px wide, collapsible to an icon strip (Fitts: ≥44px toggle handle)
- Type icons are ≥48×48px drop targets — large enough for comfortable drag (Fitts)
- Drag starts on `mousedown`/`touchstart`; a ghost image of the typed icon follows cursor

**Right-click context menu (edit mode):**
- Published device: "Remove from View" → confirm dialog → removes node + connections from View
- Draft device: "Delete Draft" → confirm dialog → permanent deletion from canvas
- Draft device: "Publish to Inventory" → publishes to global inventory
- Published device: no "Delete" or "Publish" option (already published; inventory deletion is HT-052)

**On-drop form:**
- Appears as a floating popover anchored to the drop position (not a full modal — keeps spatial context)
- "Name" field is auto-focused; Enter submits; Escape cancels
- If user clicks anywhere outside the popover without submitting, it cancels (Norman: constraints prevent incomplete commits)

**Draft node visual:**
- Dashed border (2px dashed, 60% opacity fill)
- Small "Draft" pill badge in top-right corner of node
- Tooltip on hover: "Not published to inventory yet. Click Publish to save."

**Publish button placement:**
- In the **detail panel** when a draft device is selected: a prominent "Publish to Inventory" button at the top of the panel (orange/amber, ≥44px height — Fitts: easy target, close to the content the user just filled in)
- In the **right-click context menu**: "Publish to Inventory" item (only on draft nodes)
- **Toolbar**: a "{N} drafts" counter badge (informational, not actionable) — greys out when zero

## Notes for Architect / Engineer
**Draft device storage in `cytoscape_json`:**
- Draft element data should include: `draft: true`, `draft_name`, `draft_type`, `draft_ip`, `draft_mac`, `draft_os`, `draft_notes`. The `id` field of the element is a temporary client-generated UUID (prefix `draft-`) that is replaced with the real device UUID after Publish.
- After Publish, the element's `id` and `data.id` are updated in-place to the server-assigned UUID; `draft: true` is removed. This update must be reflected in `cytoscape_json` via an autosave flush immediately after a successful Publish.

**Publish API — Architect to design, options:**
1. Individual `POST /api/devices/` per draft — simplest, clear error per device, consistent with per-device UX. Product prefers this approach.
2. `POST /api/devices/batch` — batch endpoint, returns array of results. Only needed if per-device roundtrip latency is problematic (unlikely for single-digit drafts).

**`topology_data.py` change:** Must stop auto-loading all devices. Only load devices whose IDs appear in the View's `cytoscape_json` elements (opt-in placement). Draft elements with `draft: true` are reconstructed from their local data — no DB fetch needed for them.

**Depends on:** HT-048 (edit mode gate), HT-047 (View context).
**Supersedes:** The current `topology_data.py` behaviour of loading all inventory devices onto every canvas.
