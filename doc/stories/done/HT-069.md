# HT-069: Topology Layout Rename Replaces Names Correctly

**Status:** Superseded
**MoSCoW:** Must
**Kano:** Basic — saved layouts are a core topology workflow. If renaming corrupts the name itself, users lose trust in layout management immediately.
**Phase:** 1 (Hometower)
**Size:** S (1-2 days)

## Job-to-be-Done
As a user organizing multiple topology layouts, I want renaming a layout to replace the existing name exactly so that my saved views remain readable and intentional.

## Context
Superseded on 14 April 2026 by HT-072 after the product model shifted from user-managed layouts to `Topology / History`.

HT-029 shipped layout save/load/rename/delete. The user simulation on 14 April 2026 found a concrete rename defect: renaming `My Layout` to `Lab-Primary-Topology-Name-With-Special_#01` produced `My LayoutLab-Primary-Topology-Name-With-Special_#01` instead of replacing the old value.

This is a shipped-feature regression in a core topology workflow. It is especially damaging because users often rename layouts late in a session after organizing a complex canvas.

## Acceptance Criteria

### Rename correctness
- Given I have a saved layout selected, when I click **Rename layout**, then the dialog input is prefilled with the current layout name
- Given I replace the current name with a new one and submit, when the rename succeeds, then the resulting layout name matches the submitted value exactly with no old-prefix or old-suffix concatenation
- Given the new name contains spaces, dashes, underscores, or `#`, when I submit it, then the exact text is preserved
- Given the new name is 40+ characters long, when I submit it, then it still replaces the old value exactly

### UI state after rename
- Given the rename succeeds, when the response returns, then the dialog closes and the selected layout dropdown updates immediately to the new name
- Given I refresh the page after a successful rename, when the topology page reloads, then the renamed layout still appears with the correct value
- Given the rename fails due to duplicate or invalid input, when the dialog stays open, then I see a clear inline validation message and the original saved value is unchanged

### Regression protection
- Given the unit/execution tests run, when rename input replacement is exercised, then no append/concatenate behavior regresses
- Given the browser proof test runs, when it executes the real rename flow on `/topology`, then the final dropdown value equals the submitted replacement string exactly

## Non-Goals (explicitly out of scope)
- New layout-management features beyond rename correctness
- Cross-workspace layout move/copy workflows
- Bulk rename or slug-generation rules
