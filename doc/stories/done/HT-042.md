# HT-042: Device Attachments & Photos

**Status:** Done
**MoSCoW:** Should
**Kano:** Performance — every competitor (Homebox, NetBox, Snipe-IT, Shelf) supports file attachments. Homelabbers photograph their racks, save wiring diagrams, attach warranty PDFs and invoices. Without this, Hometower can't be the single source of truth for a homelab.
**Phase:** 1 (Hometower)
**Size:** M (2–3 days)

## Job-to-be-Done
As a homelab owner, I want to attach photos (rack shots, wiring close-ups) and documents (warranty PDFs, invoices, manuals) to devices so that all information about a piece of hardware lives in one place.

## Context
The Device model has text fields (name, type, IP, notes) and relational metadata (tags, custom fields, location). But there's no way to upload files. When a homelabber sets up a new rack, they want to:

1. Photograph the front and back of the rack
2. Attach the UPS warranty PDF
3. Save the switch port mapping diagram
4. Upload the receipt for insurance purposes

This story adds a file attachment system scoped to devices. Files are stored on the server's filesystem (in a Docker volume), not in the database.

## Acceptance Criteria

### Upload
- Given I am on a device's detail panel (HT-010) as Contributor or Admin, when I see the Attachments section, then I see a dropzone / "Upload" button
- Given I click Upload (or drag-and-drop), when I select a file, then the file is uploaded via `POST /api/devices/{id}/attachments` as `multipart/form-data`
- Given the upload succeeds, when the API responds, then the file appears in the attachment list with: filename, file size (human-readable), upload date, and thumbnail (for images) or file-type icon (for non-images)
- Given I upload an image (JPEG, PNG, WebP), when the upload completes, then a thumbnail (150×150px, aspect-ratio preserved) is generated server-side and stored alongside the original

### Limits
- Given a file exceeds 10 MB, when I try to upload, then the API returns `413` and the UI shows an error toast: "File too large (max 10 MB)"
- Given a file has a disallowed extension (e.g. `.exe`, `.sh`, `.bat`), when I try to upload, then the API returns `422` and the UI shows: "File type not allowed"
- Given a device has 20 attachments already, when I try to upload a 21st, then the API returns `422`: "Maximum 20 attachments per device"

### Allowed file types
`jpg`, `jpeg`, `png`, `webp`, `gif`, `pdf`, `txt`, `md`, `csv`, `json`, `yaml`, `yml`, `doc`, `docx`, `xls`, `xlsx`

### Viewing
- Given a device has image attachments, when I view the Attachments section, then images show as clickable thumbnails in a grid
- Given I click a thumbnail, when the lightbox opens, then I see the full-resolution image with left/right navigation if multiple images exist
- Given a device has non-image attachments, when I view the list, then each shows: file icon, filename (linked for download), size, and date

### Download
- Given I click a filename or download icon, when the browser responds, then the file downloads via `GET /api/devices/{id}/attachments/{attachment_id}/download`
- Given the file is served, when headers are set, then `Content-Disposition: attachment` forces download (not inline rendering)

### Delete
- Given I am Contributor or Admin, when I click the delete button on an attachment, then a confirmation dialog appears: "Delete {filename}?"
- Given I confirm, when the API responds, then the file is removed from disk and the attachment record is deleted from the database
- Given I am Reader, when I view attachments, then no delete button is shown

### RBAC
- Given I am Reader, when I view the detail panel, then I can see and download attachments but cannot upload or delete

## Non-Goals (explicitly out of scope)
- Attachments on connections, locations, or tags (device-only for v1)
- Image editing / cropping
- OCR or text extraction from PDFs
- Virus scanning of uploads
- Cloud storage backends (S3, etc.) — local filesystem only for v1
- Drag-to-reorder attachments
- Attachment descriptions / captions

## Open Questions
None.

## Notes for Architect / Engineer
- **Storage path**: `/data/attachments/{device_id}/{uuid}.{ext}` inside the Docker volume. Never use user-supplied filenames as filesystem paths (security — path traversal prevention).
- **Database model**: New `Attachment` SQLModel: `id` (UUID), `device_id` (FK), `filename` (original name), `stored_path` (server path), `content_type` (MIME), `size_bytes` (int), `created_at`. New Alembic migration.
- **Thumbnail generation**: Use Pillow (`PIL`) — already a transitive dependency. Generate on upload, store as `{uuid}_thumb.{ext}`.
- **API endpoints**:
  - `POST /api/devices/{id}/attachments` — upload (multipart)
  - `GET /api/devices/{id}/attachments` — list
  - `GET /api/devices/{id}/attachments/{att_id}/download` — download file
  - `DELETE /api/devices/{id}/attachments/{att_id}` — delete
- **Security**: Validate MIME type server-side (don't trust `Content-Type` header). Use `python-magic` or check file signatures. Serve files with `X-Content-Type-Options: nosniff`. SVG uploads are excluded from v1 to avoid inline executable-content risk.
- **Docker volume**: Add a named volume `attachments` in `docker-compose.yml` mapped to `/data/attachments` inside the container.
