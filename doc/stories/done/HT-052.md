# HT-052: Inventory device deletion with orphan indicator

**Status:** Ready
**MoSCoW:** Must
**Kano:** Basic — users must be able to permanently remove devices from inventory. Without this, the inventory grows monotonically and old/decommissioned devices clutter search results and stencil panels.
**Phase:** 1 (Hometower)
**Size:** S (1 day)

## Job-to-be-Done
As a homelab owner, I want to permanently delete a device from my inventory — with clear warning about which Views reference it — so that I can keep my inventory clean after decommissioning hardware or correcting mistakes.

## Context
HT-051 establishes that removing a device from a View's canvas does NOT delete it from inventory. Published devices persist in the global `devices` table until explicitly deleted. This story provides the permanent deletion path and an orphan indicator to help users identify devices that exist in inventory but aren't placed on any View.

**Design decisions (resolved 12 Apr 2026):**
- Deletion is available on the **inventory page only** — not from the canvas. The canvas offers "Remove from View" (HT-051) but never "Delete from Inventory".
- Any device can be deleted, whether orphaned or placed on Views. If placed, the user is warned and deletion cascades removal from all Views.
- Un-publish (reverting a published device to draft) is **not supported** — see HT-051 Non-Goals.

## Acceptance Criteria

### Delete from inventory
- Given I am on the inventory list (HT-009) or device detail panel (HT-010), when I click the "Delete" action on a device, then a confirmation dialog appears.
- Given the device is **not placed on any View** (orphaned), then the confirmation reads: "Permanently delete [name]? This will remove it from your inventory and cannot be undone."
- Given the device **is placed on one or more Views**, then the confirmation reads: "This device appears on {N} View(s): [View 1 (Topology A), View 2 (Topology B), …]. Deleting it will remove it from all Views and permanently delete it from inventory. This cannot be undone."
- Given the user confirms deletion, then the device is deleted from the `devices` table (cascade: connections, tags, custom fields), removed from every View's `cytoscape_json` that references it, and the inventory list refreshes.
- Given the user cancels, then nothing happens.
- Given a `Reader` role user views the inventory, then the "Delete" action is not visible (RBAC: write required).

### Orphan indicator
- Given the inventory list displays devices, then each device that is **not placed on any View** shows an "Orphaned" badge/icon (e.g. a small unlinked icon or subtle label).
- Given the inventory list has a filter bar, then an "Orphaned only" filter option is available that shows only devices not placed on any View.
- Given a device is placed on at least one View, then no orphan badge is shown for that device.

### Edge cases
- Given a device is deleted while another user has that View open, when their canvas next autosaves or refreshes, then the deleted device node disappears from their canvas (eventual consistency — no real-time push required in v1).
- Given a device has connections to other devices, when it is deleted, then those connections are also cascade-deleted from both the `connections` table and from every View's `cytoscape_json`.
- Given the last device on a View is deleted from inventory, then the View becomes empty but still exists.

## Non-Goals (explicitly out of scope)
- Soft delete / trash / recycle bin (device is permanently removed)
- Bulk deletion from inventory (covered by HT-031 bulk operations)
- Deletion from the canvas context menu — canvas only offers "Remove from View" (HT-051)
- Un-publish / revert to draft (explicitly ruled out in HT-051)
- Real-time push notification to other open sessions when a device is deleted

## UX Interaction Spec

**Inventory list delete action:**
- "Delete" button/icon per row, right-aligned in the actions column. Red/destructive colour. ≥36px click target (Fitts).
- On hover: tooltip "Delete device from inventory".
- Disabled + hidden for Reader role (RBAC).

**Device detail panel delete action:**
- "Delete Device" button at the bottom of the detail panel, full-width, red/destructive styling. Separated from other actions by a divider (Norman: constraints — spatial separation prevents accidental clicks on adjacent actions).

**Confirmation dialog:**
- Modal with destructive styling (red confirm button labelled "Delete Permanently", grey cancel button).
- If placed on Views: the View list is shown as a bulleted list inside the dialog so the user sees exactly what's affected.
- Confirm button requires the user to type the device name for devices placed on ≥3 Views (extra friction for high-impact deletes).

**Orphan badge:**
- Small icon (unlink/broken-chain icon, ~16px) next to the device name in the inventory list.
- Tooltip: "Not placed on any View".
- Filter: checkbox in the filter bar: "☐ Orphaned only".

## Notes for Architect / Engineer
- **View membership query**: To determine which Views a device appears on, scan `diagram_layouts.cytoscape_json` for elements whose `data.id` matches the device UUID. This could be done via a JSON query (`cytoscape_json::jsonb @> ...`) or by maintaining a materialized `view_device_placement` table. Architect should decide — JSON scan is simpler but O(n) across all Views; a placement table is faster but adds write overhead on every canvas save.
- **Cascade removal from `cytoscape_json`**: On device deletion, every View's `cytoscape_json` that contains the device's element (and edges connected to it) must be updated. This is a server-side operation in the deletion service — not client-side.
- **Orphan detection**: A device is orphaned if its UUID does not appear in any View's `cytoscape_json` elements. Same query strategy as above.
- **API**: `DELETE /api/devices/{id}` already exists (HT-002). Extend the response or add a pre-flight `GET /api/devices/{id}/placements` that returns the list of Views referencing it, so the UI can show the warning before confirming.
- **Depends on**: HT-047 (Views exist), HT-051 (opt-in placement model — devices are placed explicitly, not auto-loaded).
