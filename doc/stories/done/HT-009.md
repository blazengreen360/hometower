# HT-009: Inventory List View (Searchable Table)

**Status:** Done
**MoSCoW:** Must
**Kano:** Basic — "Where is device X?" is the most common question any inventory tool must answer
**Phase:** 1 (Hometower)
**Size:** M (3-4 days)

## Job-to-be-Done
As a homelab owner, I want a searchable, filterable list of every device I own so that I can find a specific device in under three seconds without hunting around the topology canvas.

## Context
The topology canvas (HT-003) is the primary mental model, but scanning it for "where is the NAS with IP 192.168.1.42" is slow once you have more than 20 nodes. The inventory list is the fast lookup surface — a virtual-scrolled table with real-time filter chips and text search.

Column spec is locked by the UX-Designer agent: icon, name, type badge, IP, location, tags, updated_at. Row click navigates to `/topology?device_id={id}` (same contract HT-008 uses). Real search/filter logic is lightweight here — HT-020 covers the full search semantics (operators, advanced filters); HT-009 handles the core path.

## Acceptance Criteria
- Given I am authenticated and navigate to `/inventory`, when the page loads, then I see a table with columns: icon, name, type badge, IP, location, tags, updated_at
- Given I have 50+ devices, when the table renders, then virtual scrolling keeps the DOM node count under 100 and the initial render stays under 500ms
- Given I type in the search box, when 200ms of idle passes, then the table filters in place across name, IP, and notes (case-insensitive substring match)
- Given I click a DeviceType chip in the filter bar, when the chip activates, then the table filters to only that device type; clicking the chip again deactivates it
- Given I click a Tag chip in the filter bar, when the chip activates, then the table filters to devices carrying that tag; multiple active tag chips act as OR
- Given a DeviceType chip AND a Tag chip are both active, when the filter runs, then only devices that match BOTH (AND across filter categories, OR within a category) are shown
- Given filters are active and match zero devices, when the table renders, then the empty state shows "No devices match — try clearing filters" with a "Clear filters" button
- Given I click a row, when the navigation fires, then I go to `/topology?device_id={id}` and the device is pre-selected on the canvas
- Given I sort by a column, when I click the column header, then the rows reorder ascending; clicking again sorts descending
- Given the table contains an IP address or MAC, when the cell renders, then those values use the monospace token from the design system
- Given I hover over an IP or MAC cell, when the hover fires, then a small clipboard icon appears; clicking it copies the value and shows a success toast

## Non-Goals (explicitly out of scope)
- Advanced query operators (`type:server ip:192.168.*`) — HT-020 covers that
- Export-from-list (the list is a view, not an export surface — HT-012/HT-013 cover JSON export/import)
- Bulk actions (multi-select + delete/tag/move) — Phase 2
- Saved filters or saved views
- Per-column visibility toggle
- Grouped rows (group by type or location)
- Server-side pagination — v1 uses client-side virtual scroll (the 50-device scale target fits in memory easily)

## Open Questions
None — column set, filter semantics, and search scope are locked by the UX-Designer spec.

## Notes for Architect / Engineer
- Page at `src/ui/pages/inventory.py`
- Consumes `GET /api/devices` (already exists from HT-002) — extend the response to include `tags` (from HT-006) and `location.name` (via `?include=location,tags`); add these query params to the device router if not already present
- Virtual scroll: use NiceGUI's `ui.table` with virtual scroll enabled, OR drop to a custom `ui.aggrid` if the built-in table can't hit the 100-DOM-node / 500ms target
- Search debounce: 200ms on the text input `on_change` handler
- Filter state lives in Python-side reactive state; column sorting happens client-side
- Pure filter function in `src/domain/inventory.py`: `filter_devices(devices: List[DeviceRead], search: str, types: Set[DeviceType], tag_ids: Set[UUID]) -> List[DeviceRead]` — fully unit-testable with zero mocks
- Design tokens: type-badge colours from `src/ui/design/tokens.py`, monospace font for IPs/MACs, clipboard icon from Material Icons
- File size: if `inventory.py` exceeds 250 lines, extract filter UI into `src/ui/components/inventory_filter_bar.py` (test files in `tests/` exempt from the limit)
- Accessibility: column headers keyboard-focusable, sort toggled by Enter/Space, clipboard-copy announced via `aria-live="polite"`
- RBAC: read-only page, available to all authenticated users
- Performance budget: initial render ≤ 500ms for 200 devices; search response ≤ 50ms after debounce
