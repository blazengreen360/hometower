# HT-000: Phase 1 Architecture Design and Review

**Status:** Done
**MoSCoW:** Must
**Phase:** 1 (Hometower)
**Size:** L (5-7 days)

## Job-to-be-Done
As the engineering team, we need a complete architectural blueprint for Hometower Phase 1 so that all feature work follows consistent patterns and the system remains maintainable.

## Context
Before any feature implementation begins, we need a comprehensive architecture document that defines:
- Layer boundaries and import rules
- Database schema and migration strategy
- API contracts and validation approach
- NiceGUI + Cytoscape.js integration pattern
- Authentication and authorization flow
- Error handling and logging conventions
- Test strategy (unit, integration, E2E)
- Docker Compose orchestration
- Configuration management (.env strategy)

This RFC serves as the blueprint for all subsequent feature stories (HT-001 through HT-020).

## Acceptance Criteria
- Given the architecture document is complete, when I read the layer rules section, then I can determine which layer owns each responsibility and which imports are allowed
- Given the architecture document is complete, when I read the database schema section, then I see all tables, columns, indexes, and foreign key relationships for Phase 1
- Given the architecture document is complete, when I read the API contracts section, then I see example request/response payloads for all core endpoints
- Given the architecture document is complete, when I read the NiceGUI integration section, then I understand how Cytoscape.js and Leaflet.js are embedded and how events flow between JavaScript and Python
- Given the architecture document is complete, when I read the auth flow section, then I see a sequence diagram showing login, JWT validation, and RBAC enforcement
- Given the architecture is reviewed, when the Code-Reviewer audits it, then zero architectural violations or anti-patterns are found
- Given the architecture is approved, when Feature-Engineer reads it, then all open questions blocking HT-001, HT-002, and HT-003 are resolved

## Non-Goals (explicitly out of scope)
- Phase 2 / LightTower architecture (multi-workspace, auto-discovery, LDAP/SSO)
- Performance optimization strategies (premature for v1)
- Deployment to cloud providers (Docker Compose on self-hosted hardware only)
- Monitoring and observability integrations (not in v1)

## Open Questions
None — the requirements are clear from AGENTS.md and memory/project_hometower.md.

## Notes for Architect
**Deliverables expected:**
1. `doc/architecture/rfc-001-phase1-architecture.md` — Complete system design
2. `doc/architecture/schema.sql` — PostgreSQL schema DDL (reference for Alembic migrations)
3. `doc/architecture/api-contracts.yaml` — OpenAPI 3.0 specification for all Phase 1 endpoints
4. `doc/architecture/diagrams/` — Sequence diagrams for auth flow, canvas interaction, and map rendering

**Key constraints from AGENTS.md:**
- Files ≤ 250 lines (hard cap 400). If any document exceeds this, split it.
- Strict layered architecture: `UI → API → Services → Domain → Repositories → PostgreSQL`
- `src/domain/` must contain pure functions only (no I/O, no network, no database imports)
- `src/ui/` never imports from `src/repositories/` directly
- Loguru only (no `print()` or `logging.*`)
- Pydantic validates all API input before service layer
- Passwords always bcrypt via `src/utils/auth.py`
- JWT with HS256, 24-hour expiration, enforced in `src/api/middleware/auth.py`

**Tech stack (non-negotiable):**
- NiceGUI + Cytoscape.js + Leaflet.js
- FastAPI mounted via `ui.run_with()`
- SQLModel + Alembic
- PostgreSQL 16
- Docker Compose

**Review gate:**
After Architect completes the RFC, Code-Reviewer must audit it against the rejection matrix in AGENTS.md before it's marked Done.
