# HT-032: Canvas Undo/Redo

**Status:** Done
**MoSCoW:** Should
**Kano:** Performance — every canvas interaction is a database write. Accidental deletions or moves with no undo create anxiety. Undo transforms the canvas from "scary permanent" to "safe to experiment."
**Phase:** 1 (Hometower)
**Size:** M (2–3 days)

## Job-to-be-Done
As a homelab owner editing a View in the View Designer, I want to undo and redo canvas actions so that accidental deletions, bad moves, or wrong connections can be instantly reversed without manual cleanup.

## Context
HT-003 built the interactive canvas. HT-016 adds keyboard shortcuts (Delete, Select All). But there's no undo/redo. Every canvas action on a published device (move node, draw edge, delete node, delete edge) immediately hits the API and persists to the database. An accidental Ctrl+A → Delete wipes the entire View with no recovery.

This story adds a client-side undo stack that records canvas mutations and can reverse them. For **published devices**, undo calls the appropriate API endpoints in reverse. For **draft devices** (HT-051), undo is purely local — it modifies the View's `cytoscape_json` only, since drafts don't exist in the `devices` table.

## Acceptance Criteria

### Core undo/redo
- Given I move a node on the canvas, when I press Ctrl+Z (Cmd+Z on macOS), then the node returns to its previous position and the layout is re-saved
- Given I draw a new connection (edge), when I press Ctrl+Z, then the connection is deleted via the API and removed from the canvas
- Given I delete a published device node, when I press Ctrl+Z, then the device is re-created via the API with its original properties and repositioned — connections that were cascade-deleted are also restored
- Given I delete a draft device node (unpublished, HT-051), when I press Ctrl+Z, then the draft node is restored on the canvas locally (no API call) and the View's `cytoscape_json` is updated
- Given I remove a published device from a View (right-click → "Remove from View", HT-051), when I press Ctrl+Z, then the published device node and all its connections that were on this View are restored to the canvas and `cytoscape_json` (no API re-creation needed — the device still exists in inventory)
- Given I delete a connection, when I press Ctrl+Z, then the connection is re-created via the API
- Given I change a device's properties via the detail panel (e.g. rename), when I press Ctrl+Z, then the previous value is restored via `PATCH`
- Given I have performed undo, when I press Ctrl+Shift+Z (or Ctrl+Y), then the action is re-applied (redo)
- Given I undo an action and then perform a new action, when the new action executes, then the redo stack is cleared (standard undo/redo behaviour)

### Stack limits
- Given the undo stack has 50 entries, when a 51st action occurs, then the oldest entry is dropped (FIFO eviction)
- Given I navigate away from the View Designer page and return, when I check the undo stack, then it is empty (undo history is per-session, not persisted)

### UI indicators
- Given the undo stack is non-empty, when I look at the View Designer toolbar, then the Undo button is enabled (not greyed out)
- Given the redo stack is non-empty, when I look at the View Designer toolbar, then the Redo button is enabled
- Given both stacks are empty, when I look at the toolbar, then both buttons are greyed out
- Given I hover over the Undo button, when the tooltip appears, then it shows the action that will be undone (e.g. "Undo: Delete pihole")

### Error handling
- Given I undo a device deletion but the re-creation API call fails (e.g. a duplicate name was created in the meantime), when the error occurs, then a toast shows "Undo failed: {reason}" and the action remains in the undo stack for retry

## Non-Goals (explicitly out of scope)
- Undo for non-canvas actions (inventory table edits, settings changes, user management)
- Persistent undo history across page reloads or sessions
- Collaborative undo (multi-user conflict resolution)
- Infinite undo stack (capped at 50)
- Undo for bulk operations (HT-031)
- Undo for diagram layout save/delete (HT-029)

## Notes for Architect / Engineer
- **Architecture**: Client-side JS undo stack. Each entry is an `UndoEntry` object with `{ type: "move"|"create_edge"|"delete_node"|"delete_edge"|"remove_from_view"|"update", forward: {apiCall, data}, reverse: {apiCall, data} }`. Undo pops the stack and executes `reverse`. Redo pushes back and executes `forward`.
- **Published node deletion is complex**: Deleting a published device cascade-deletes its connections. The undo entry must capture the device AND all its connections at the moment of deletion, then re-create all of them on undo. Capture this data before calling `DELETE`.
- **Remove-from-View is simpler than deletion**: The device still exists in inventory. The undo entry only needs the Cytoscape element data + connections for this View. Undo restores them to `cytoscape_json` — no API calls. Redo removes them again.
- **Draft node deletion is simple**: Draft devices (HT-051) exist only in the View's `cytoscape_json`. Undo simply restores the Cytoscape element — no API calls needed. The undo entry must flag whether the node was `draft` or `published`.
- **Move batching**: Node drag fires many position updates. Debounce into a single undo entry: capture position at `dragstart`, record final position at `dragend`, undo restores the start position.
- **Keyboard shortcuts**: Integrate with HT-016's shortcut system. Register `Ctrl+Z` and `Ctrl+Shift+Z` / `Ctrl+Y`.
- **File**: `src/ui/components/canvas_undo.py` for the Python-side coordinator + JS undo stack injected via `ui.add_body_html()`.
