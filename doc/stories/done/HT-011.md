# HT-011: RBAC Enforcement (Admin / Contributor / Reader)

**Status:** Completed
**MoSCoW:** Must
**Kano:** Basic — users expect that a "Reader" can't delete devices. Absence causes immediate distrust in shared setups.
**Phase:** 1 (Hometower)
**Size:** M (2-3 days)

## Job-to-be-Done
As a homelab owner sharing access with family or friends, I want granular role enforcement so that Readers can browse the inventory and Contributors can edit devices without either being able to manage users or system settings.

## Context
HT-001 shipped JWT auth with `Role` enum (Admin, Contributor, Reader) and the `require_role()` FastAPI dependency. Individual routers already gate some endpoints. This story is the **systematic audit and enforcement pass** — every endpoint, every UI surface, every action button must respect the role matrix. It also adds visual enforcement (hide buttons Readers can't use) so the UI doesn't show affordances that will 403.

## Acceptance Criteria
- Given I am a Reader, when I attempt `POST`, `PATCH`, or `DELETE` on any `/api/devices/*`, `/api/connections/*`, `/api/diagrams/*`, `/api/locations/*`, `/api/tags/*` endpoint, then I receive HTTP 403
- Given I am a Reader, when I view the topology canvas, then drag-from-palette, delete-node, delete-edge, save-layout, and context-menu write actions are hidden or disabled
- Given I am a Reader, when I view the device detail panel (HT-010), then all edit pencils, add buttons, and delete icons are hidden
- Given I am a Contributor, when I attempt `DELETE /api/users/*` or `PATCH /api/users/{id}/role`, then I receive HTTP 403
- Given I am a Contributor, when I view the admin panel (HT-019), then the page redirects to `/topology` with a toast: "Admin access required"
- Given I am an Admin, when I perform any action, then no restriction applies
- Given a Reader's JWT is used in a direct API call (bypassing UI), when the role check runs, then 403 is returned with body `{"detail": "Insufficient permissions"}`
- Given I am authenticated with any role, when I `GET` any read endpoint, then I receive 200 (all roles can read everything)
- Given a new endpoint is added in the future, when it lacks a `require_role()` dependency, then the integration test suite's "all-routes-have-role-check" test catches it

## Non-Goals (explicitly out of scope)
- Per-object permissions (e.g., "Reader X can only see devices tagged 'public'") — Phase 2
- Role assignment UI — that's HT-019
- API key authentication (JWT only in v1)
- Audit logging of denied actions — Phase 2 (LT-007)
- Custom roles beyond the three built-in ones

## Open Questions
None — the three-role matrix is frozen and the `require_role()` dependency pattern is established.

## Notes for Architect / Engineer
- Central role matrix: create `src/domain/rbac.py` constant `ROLE_PERMISSIONS: dict[Role, set[str]]` enumerating allowed actions per role — unit-testable
- Integration test: parametrize across all registered FastAPI routes, assert that each has a `require_role` dependency or is explicitly allowlisted (login, health, root redirect)
- UI enforcement: pass `current_user.role` to every component; conditionally render action buttons with `ui.element.visible(role >= Role.Contributor)`
- The existing `require_role()` dependency in `src/domain/rbac.py` returns a FastAPI `Depends` — extend it to accept a minimum role level rather than an exact match (Reader < Contributor < Admin)
- Do NOT duplicate role checks — service layer should not re-check what the router dependency already enforced
- File: update existing `src/domain/rbac.py`; no new files expected unless the permission matrix grows beyond 250 lines
