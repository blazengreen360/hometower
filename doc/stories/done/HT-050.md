# HT-050: Node and container drag resize

**Status:** Ready
**MoSCoW:** Could
**Kano:** Performance — more layout control = more satisfaction; users with dense racks expect to size containers to reflect relative physical scale
**Phase:** 1 (Hometower)

## Job-to-be-Done
As a homelab author, I want to resize nodes and containers by dragging their edges so that I can communicate the relative scale or importance of infrastructure components visually in my diagrams.

## Context
Cytoscape.js does not support drag resize natively. This story adds resize handles (small squares at the four corners and four edge midpoints) that appear when a node or container is selected in edit mode. Dragging a handle updates the node's width and height live. The final size is stored per-View in the View's `cytoscape_json` so different Views can have different sizes for the same device. Only active in edit mode (HT-048).

## Acceptance Criteria
- Given a node or container is selected in edit mode, then 8 resize handles (4 corners + 4 edge midpoints) appear at its boundary.
- Given the user drags a corner handle, then the node resizes proportionally (both width and height change, aspect ratio maintained).
- Given the user drags an edge-midpoint handle, then only the corresponding dimension changes (left/right = width, top/bottom = height).
- Given the user releases the handle, then the new dimensions are committed: the canvas element's `style.width` and `style.height` are updated and an autosave is triggered within the normal debounce window.
- Given a minimum size constraint, a node cannot be resized smaller than 40 × 40 px (icon + label must remain legible).
- Given a node is deselected, then the resize handles disappear.
- Given a container is resized to be smaller than its children's bounding box, then the resize is clamped: the container cannot be shrunk smaller than `childrenBoundingBox + padding` (Cytoscape enforces this automatically for compound nodes; verify behaviour).
- Given the layout is saved and reloaded, then the node appears at its resized dimensions.

## Non-Goals (explicitly out of scope)
- No snap-to-grid in this story.
- No per-device global default size (size is View-specific only).
- No resize in view-only mode.
- No maximum size constraint.
- No resize undo — use HT-032 for undo/redo once that story is built.

## Notes for Architect / Engineer
**Implementation options — Architect must choose before Feature-Engineer starts:**
1. **`cytoscape-node-resize` npm plugin** — drop-in, provides handles. Evaluate licence (MIT), bundle size, and compatibility with our Cytoscape version before adopting.
2. **Custom HTML overlay** — absolutely-positioned `<div>` handles rendered over the canvas, repositioned on `position` and `style` events. More work but no external dependency and consistent with our embedded JS architecture pattern.
3. **Custom Cytoscape extension** — write a small Cytoscape plugin inline in `canvas_js.py` / `canvas_js_utils.py`. Fits our existing architecture best.

**Persistence:**
- Store as `style: { width: Npx, height: Npx }` on each element in `cytoscape_json`. On load, apply via `cy.style(...)` or by setting element style directly.
- The autosave path (`_htFlushAutosave` in `canvas_js_utils.py`) already captures the full element state via `cy.json()` — no additional serialisation needed if Cytoscape inline styles are set.

**Depends on:** HT-048 (handles only active in edit mode).
