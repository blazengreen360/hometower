# HT-073: Personal Topology Drafts with Autosave

**Status:** Done
**MoSCoW:** Must
**Kano:** Basic — users expect in-progress topology work to be protected without polluting saved history with accidental or low-signal checkpoints.
**Phase:** 1 (Hometower)
**Size:** M (2-3 days)

## Job-to-be-Done
As a Contributor, I want autosave to protect my in-progress topology edits as a personal draft so that I can safely resume work without cluttering shared history.

## Context
The same 14 April 2026 design session drew a hard product boundary:

- **Explicit Save Version** creates shared, immutable topology history
- **Autosave** must not create history versions
- In-progress work should persist as a **server-side personal draft**

Drafts are private to the editing user. They are on by default. They exist to protect work-in-progress, not to become a second visible history system.

## Acceptance Criteria
- Given I edit a topology as a Contributor or Admin, when autosave runs, then my changes are persisted to a server-side personal draft for that topology without creating a new history version
- Given I leave a topology with a personal draft and return later on the same account, when the page loads, then my latest personal draft resumes with visible draft status
- Given another user opens the same topology, when they load the page, then they do not see my draft and instead see their own draft if one exists or the latest saved topology version if not
- Given I click **Save Version** while a personal draft is active, when the save succeeds, then the current draft contents become a new history version and the draft is no longer treated as unsaved work
- Given autosave is enabled by default, when a user opens the topology editor for the first time, then draft protection is active without any extra setup
- Given a Reader opens a topology, when they view it, then no personal draft edit state is created because they cannot modify the topology

## Non-Goals (explicitly out of scope)
- Real-time collaborative editing or shared drafts
- Draft diffing against the latest saved version
- User-managed draft naming
- Cross-user draft takeover or merge flows

## Open Questions
None.

## UX Interaction Spec
- **Placement:** a subtle `Draft` status chip appears near the topology title and `Save Version` button when the personal draft differs from the latest saved version.
- **Interaction triggers:** normal editing actions continue to autosave in the background; no extra save action is needed to keep a personal draft alive.
- **State transitions:** saved topology -> dirty draft -> autosaving indicator -> `Draft` state -> `Save Version` publishes the draft into History and clears the draft-dirty state.
- **Edge-case constraints:** draft state is private per user; Readers never see editing affordances; autosave must not create visible history spam.
- **Fitts's Law justification:** `Save Version` remains the deliberate primary action because turning a draft into shared history is high-value and should be easy to hit. The draft chip is informational and therefore visually present but not dominant.

## Notes for Architect / Engineer
- Reuse HT-058's autosave reliability improvements, but change the product destination of autosave from "latest layout/version" to "personal draft".
- Draft storage should be keyed by topology + user.
- Keep the visible model simple: users should feel "my unsaved work is safe" without having to browse a separate drafts table.
- Draft persistence is server-side so it survives refresh, navigation, and browser restarts.
