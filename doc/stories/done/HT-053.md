# HT-053: Ownership scoping for legacy `/api/diagrams/` endpoints

**Status:** Done
**MoSCoW:** Must
**Kano:** Basic — multi-user Hometower (HT-019 enabled multiple users in Phase 1) means one user can already read or mutate another user's diagram layouts via the unguarded legacy endpoints. Absence of this fix is a real, exploitable IDOR in any deployment with more than one user.
**Phase:** 1 (Hometower)
**Size:** S (1 day)
**Shipped:** 13 April 2026

## Job-to-be-Done
As a Hometower admin operating a shared instance, I want every diagram-layout API operation limited to the requesting user's own Views so that one user's canvas data is never visible to or modifiable by another user.

## Context
HT-047 introduced the Workspace → Topology → View ownership chain:
`diagram_layouts.topology_id → topologies.workspace_id → workspaces.owner_id`

The legacy CRUD endpoints at `/api/diagrams/` predate workspaces and have no ownership filter. They were written when Hometower was effectively single-user. HT-019 shipped Admin User Panel — multiple real users now exist. Code-Reviewer flagged this as an IDOR during HT-047 review; it was triaged as pre-existing and deferred to this story.

**Affected endpoints:**
- `GET /api/diagrams/` — returns ALL diagram layouts, regardless of who owns them
- `GET /api/diagrams/{id}` — returns any layout by UUID with no ownership check
- `PATCH /api/diagrams/{id}` — mutates any layout
- `PUT /api/diagrams/{id}` — replaces any layout (autosave path)
- `DELETE /api/diagrams/{id}` — deletes any layout
- `POST /api/diagrams/` — creates layout, but `topology_id` is not verified to belong to caller

**Ownership verification strategy:**
Walk the FK chain: `DiagramLayout → Topology → Workspace → owner_id == requesting user`.  
The service layer already performs this pattern for workspace and topology endpoints (HT-047). Extend it here.

For `GET /api/diagrams/` (list all), scope to the calling user's layouts — join through the topology → workspace chain.

For backward compat with the canvas autosave `PUT /api/diagrams/{id}`, the ownership check must still pass — the same user who created the layout is always the one autosaving.

## Acceptance Criteria

### Ownership filter on list
- Given User A and User B each have diagram layouts, when User A calls `GET /api/diagrams/`, then only User A's layouts are returned (User B's are excluded).

### Ownership check on get
- Given a diagram layout owned by User A, when User B calls `GET /api/diagrams/{layout_id}`, then the response is `404 Not Found`.
- Given a diagram layout owned by User A, when User A calls `GET /api/diagrams/{layout_id}`, then `200 OK` with the layout is returned.

### Ownership check on write operations
- Given a layout owned by User A, when User B sends `PATCH /api/diagrams/{layout_id}`, then `404 Not Found`.
- Given a layout owned by User A, when User B sends `PUT /api/diagrams/{layout_id}` (autosave), then `404 Not Found`.
- Given a layout owned by User A, when User B sends `DELETE /api/diagrams/{layout_id}`, then `404 Not Found`.

### Ownership check on create
- Given User B sends `POST /api/diagrams/` with `topology_id` belonging to User A's workspace, then `404 Not Found` (topology not visible to User B).
- Given User B omits `topology_id` (legacy autosave path), then layout creation succeeds and the layout is associated with User B's default topology (or none, for backward compat).

### Admin role
- Given an Admin-role user, they are still bound by their own ownership — Admin does NOT mean cross-user access to diagram layouts. Admin privileges cover user management (HT-019), not data access.

## Non-Goals (explicitly out of scope)
- Cross-user sharing or collaboration on layouts (Phase 2 / LightTower)
- Migrating shared layouts between users
- Admin "impersonate user" view
- Any change to workspace, topology, or view endpoints — those already have ownership (HT-047)

## Notes for Architect / Engineer
- The ownership verification chain is: `DiagramLayout.topology_id → Topology.workspace_id → Workspace.owner_id`. If `topology_id` is `NULL` (legacy layout created before HT-047 migration), ownership is ambiguous — treat as owned by the first admin (matching migration 023 backfill logic).
- Service layer: add `owner_id: uuid.UUID` parameter to all `diagram_service` methods that operate on a single layout. Mirror the pattern in `workspace_service.get_by_id(workspace_id, owner_id, session)`.
- Repository layer: `diagram_repository.get_by_id_for_owner(session, layout_id, owner_id)` — join through topology/workspace, return `None` if chain breaks. Service maps `None` to `HTTPException(404)`.
- `GET /api/diagrams/` list: add a `owner_id` filter via a LEFT JOIN to `topologies` → `workspaces`. Return `[]` silently for layouts with `NULL topology_id` that are not owned (never expose them).
- `POST /api/diagrams/` (autosave without topology_id): must still succeed. The ownership check only applies when `topology_id` is provided — verify the topology belongs to the caller.
- The canvas `topology_data.py` loader calls `GET /api/diagrams/{id}` — once the ownership check is added, this continues to work because the canvas always loads the calling user's own layout.
- New unit tests: mock ownership mismatch, verify 404 is returned for each endpoint. New integration tests: two-user fixture, cross-ownership request, assert 404.
