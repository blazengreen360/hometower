# HT-055: Validation feedback in create and rename dialogs

**Status:** Done
**MoSCoW:** Should
**Kano:** Basic — silent failures violate Norman's Feedback principle. When a user submits a blank name or a duplicate name and nothing visible happens (or the dialog closes without creating anything), they are left confused and have no corrective action to take. This is a hygiene issue that undermines trust in the feature.
**Phase:** 1 (Hometower)
**Size:** S (half day)

## Job-to-be-Done
As a homelab owner, I want create and rename dialogs to tell me immediately when my input is invalid — empty, too long, or a duplicate — so that I understand why my action failed and can correct it without guessing.

## Context
E2E sweep of HT-047 (12 Apr 2026) found two silent failure cases in `show_name_dialog` (used by all workspace/topology/view create and rename actions):

1. **Empty name**: Submitting a blank name causes no visible feedback. The dialog stays open (correct behaviour) but the user sees no error message explaining why it didn't close.
2. **Duplicate name**: The API returns `409 Conflict`, the dialog closes, and no toast appears. The user sees their workspace/topology/view did not appear in the table but has no idea why.

The `show_name_dialog` in `src/ui/components/dialogs/name_dialog.py` already has an `error_label` element that is hidden by default — it just isn't wired to display validation messages.

The `on_create` / `on_rename` handlers in each page file receive API error responses and call `ui.notify(detail, type="negative")` — but the toast is suppressed when the dialog closes prematurely before the API call returns.

## Acceptance Criteria

### Empty name
- Given the create or rename dialog is open, when the user submits with an empty (or whitespace-only) name, then an inline error message "Name is required" appears below the input field within the dialog.
- Given the inline error is shown, when the user starts typing, then the error message clears.
- Given the inline error is shown, the dialog does NOT close.

### Duplicate name (API 409)
- Given the user submits a valid, non-empty name that is a duplicate (API responds `409`), then the dialog remains open and shows an inline error: "A [workspace/topology/view] with this name already exists."
- The inline error message text is specific to the entity type (not generic).
- The dialog does NOT silently close on API error.

### Other API errors
- Given the API returns any non-success status that is not `409`, then the dialog closes and a `ui.notify` toast with the error detail appears (existing behaviour preserved for unexpected errors).

### Success
- Given the API returns `201` / `200`, then the dialog closes cleanly and a positive `ui.notify` toast appears (existing behaviour preserved).

## Non-Goals (explicitly out of scope)
- Client-side uniqueness check before API call (too complex, race-prone — let the API be the source of truth)
- Validation on fields other than `name` (this dialog only has one field)
- Inline validation on other dialogs (e.g., delete confirmation — nothing to validate)

## UX Interaction Spec

**Inline error label:**
- Rendered below the input field, font-size 0.8rem, color red / `var(--ht-error)`.
- Hidden by default (using `set_visibility(False)`).
- Visible when validation fails or when API returns 409.
- Cleared (set empty + hidden) when: user starts typing, dialog is successfully submitted.

**Input border:**
- On validation error, the input field gets `color=negative` prop (Quasar `q-input` styling).
- On correction, border colour resets.

**Dialog does not auto-close on 409:**
- The existing `_submit()` function in `name_dialog.py` calls `dialog.close()` before `on_submit()`. This must change: `dialog.close()` should only be called after the API call returns successfully.
- This requires `on_submit` to signal back whether it succeeded. Change the signature to return `bool` (True = success, close dialog; False = failure, leave open and show error).

**Fitts compliance:**
- Error label does not push the dialog buttons out of the viewport. Dialog card has `max-height` or scrolls gracefully if the label is long.

## Notes for Architect / Engineer
- **`name_dialog.py` refactor**: `on_submit` callback currently returns `Awaitable[None]`. Change it to `Awaitable[str | None]` — returns an error message string on failure, `None` on success. The `_submit()` function checks the return value: if error string, display in `error_label` and keep dialog open; if `None`, close dialog.
- **Alternatively**: Pass the `error_label` reference into `on_submit` and have the caller update it directly. This avoids changing the callback return type.
- **Page-side changes**: `on_create` and `on_rename` handlers in `workspaces.py`, `workspace_detail.py`, `topology_detail.py` must either: (a) return an error string on failure, or (b) signal failure via a shared state mechanism.
- **409 message localisation**: Pass entity type name into `show_name_dialog` as an optional parameter, e.g. `entity="workspace"`, so the error reads "A workspace with this name already exists."
- All tests are UI-layer — no new integration tests needed (API 409 is already tested). Add unit/UI tests in existing test files verifying the component's error state transitions.
