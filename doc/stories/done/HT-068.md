# HT-068: Reliable JSON Export from Settings

**Status:** Ready
**MoSCoW:** Must
**Kano:** Basic — backups are table stakes. A homelab inventory tool that cannot reliably export its data at the moment an operator needs it is not trustworthy.
**Phase:** 1 (Hometower)
**Size:** S (1-2 days)

## Job-to-be-Done
As an operator preparing for a risky change or migration, I want Export JSON in Settings -> Data to reliably download a full backup so that I can recover my inventory if something goes wrong.

## Context
HT-012 shipped JSON export, and the data-management UI now exposes that workflow in Settings -> Data. The user simulation on 14 April 2026 found that an authenticated Admin clicking Export JSON receives a generic browser alert: `Export failed. Please check your session and try again.` That turns a core backup workflow into a dead end at the exact moment a user is trying to protect themselves.

This story restores trust in the export path by fixing the authenticated download flow, improving failure handling, and tightening role-aware UI behavior on the page.

## Acceptance Criteria

### Successful export path
- Given I am an authenticated Admin or Contributor on `/settings/data`, when I click **Export JSON**, then a JSON file downloads successfully without redirecting me to `/login`
- Given the export succeeds, when I open the downloaded file, then it is valid JSON and contains the full snapshot shape expected by Hometower export/import (`devices`, `connections`, `locations`, `tags`, `diagram_layouts`, `users`, `workspaces`, `topologies`, and related supporting collections)
- Given I click Export JSON repeatedly, when each request completes, then each download is valid and no stale-session alert is shown

### Failure handling
- Given the backend returns `401` or `403`, when the export request fails, then the UI shows an explicit session/permission message instead of the generic `check your session` alert
- Given the backend returns `5xx` or a network failure occurs, when the export request fails, then the UI shows a concise non-sensitive error message explaining that the backup was not created
- Given the export request fails, when the error is shown, then no misleading success state or empty file is produced

### Role-aware UI
- Given I am a Reader on `/settings/data`, when the page renders, then the export action is unavailable or disabled with a clear explanation that export requires Contributor or higher
- Given I am an Admin or Contributor, when the page renders, then the export action is visibly enabled

### Verification
- Given the fix is implemented, when the browser proof test runs, then it verifies a real authenticated export click path from `/settings/data`
- Given the API integration tests run, when export is called with valid auth, then the response is `200` with a downloadable JSON payload

## Non-Goals (explicitly out of scope)
- Import flow changes
- Export-to-PNG/SVG (covered separately by HT-014)
- New backup formats beyond the existing Hometower JSON export
- Scheduled or automatic backups

None.

## Notes for Architect / Engineer
- Likely touch points: `src/ui/pages/settings_data.py`, export-download JS bridge, and the `/api/export` route behavior
- Browser proof is required because the current defect is in the real click/download flow, not just the API response
- Preserve HT-064 rate limiting and existing auth/RBAC boundaries on export
- Prefer toast/inline notification behavior over raw `window.alert(...)` for non-blocking failures if consistent with the current UI patterns
