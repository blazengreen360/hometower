# HT-075: Restore History Safely When Inventory Devices Were Deleted

**Status:** Ready
**MoSCoW:** Must
**Kano:** Basic — history loses credibility if restoring an older topology silently resurrects deleted inventory records or drops them without explanation.
**Phase:** 1 (Hometower)
**Size:** M (2-3 days)

## Job-to-be-Done
As a homelab owner reviewing or restoring older topology history, I want deleted devices to appear as clearly marked historical ghosts so that the diagram stays legible without undoing inventory deletion automatically.

## Context
The product decision from 14 April 2026 is explicit:

- Restoring History is a **topology restore**, not an inventory rollback
- A device deleted from inventory stays deleted
- If an older topology version references deleted devices, the restored diagram shows **ghost placeholders** in those historical positions
- Ghosts can offer deliberate recovery actions, but nothing is recreated automatically

This keeps inventory as the source of truth while preserving the explanatory value of history.

## Acceptance Criteria
- Given I restore a topology version that references devices later deleted from inventory, when the restore completes, then the topology is restored without automatically recreating those deleted inventory records
- Given missing device references exist in the restored version, when the canvas loads, then each missing device appears as a non-editable ghost placeholder in its historical position with clear `Deleted from inventory` labeling
- Given a restored topology contains ghost placeholders, when the page finishes loading, then I see a restore summary explaining that deleted devices were preserved as ghosts rather than restored into inventory
- Given I select a ghost placeholder as a Contributor or Admin, when its details are shown, then I can choose `Recreate as New Device` or `Map to Existing Device`
- Given I choose `Recreate as New Device`, when the action completes, then a new inventory record is created as a draft/pending-review device and the ghost is replaced by that draft-backed device in the topology
- Given I choose `Map to Existing Device`, when I select a current device, then the ghost is replaced by the chosen live device in that topology version
- Given I am a Reader, when I view restored ghost placeholders, then I can see them and their deleted status but no recovery actions are available

## Non-Goals (explicitly out of scope)
- Automatic inventory resurrection during restore
- Bulk ghost reconciliation workflows
- Restoring deleted devices with their full audit/version history intact
- Cross-topology remapping suggestions

## Open Questions
None.

## UX Interaction Spec
- **Placement:** ghost placeholders render inline on the canvas; the explanatory summary appears as a persistent banner near the top of the topology view after restore.
- **Interaction triggers:** restore an older version -> ghost placeholders appear automatically for missing devices -> selecting a ghost opens its detail actions.
- **State transitions:** restored version loads -> deleted-device banner appears -> user either leaves ghosts as historical markers or resolves them one by one via recreate/map actions.
- **Edge-case constraints:** restore is still considered successful even if ghosts remain unresolved; Readers stay view-only; ghost placeholders are visibly different from active devices.
- **Fitts's Law justification:** recovery actions live in the selected ghost's detail surface rather than on every canvas node, which prevents accidental recreation while keeping the deliberate recovery path close to the affected object.

## Notes for Architect / Engineer
- Inventory remains the source of truth. History restore must never silently recreate deleted rows.
- Ghost placeholders should preserve enough metadata to explain what used to be there (for example prior device name/type) without pretending the device is live.
- `Recreate as New Device` should create a new draft/pending-review device rather than immediately publishing a replacement into inventory.
- `Map to Existing Device` is a topology-level reconciliation action, not a hidden inventory mutation.
