# HT-010: Device Detail Panel

**Status:** Done
**MoSCoW:** Must
**Kano:** Basic for read; Performance for inline-edit — the faster users can fix wrong metadata, the more they'll trust the inventory
**Phase:** 1 (Hometower)
**Size:** S (1-2 days)

## Job-to-be-Done
As a homelab owner, I want to see everything I know about a device in one focused panel and edit simple fields in place so that I can update metadata without losing my spatial context on the canvas.

## Context
HT-003 opens a "detail panel" placeholder when a canvas node is selected, but only shows name/type/IP/MAC/notes in a static layout. HT-010 delivers the real panel: a slide-in right sidebar with proper sections (Identity, Location, Tags, Custom Fields, Notes, Connections), inline editing for simple fields, and navigation links to connected devices.

The panel is reused across three surfaces:
1. Topology canvas (HT-003) — opens when a node is selected
2. Inventory list (HT-009) — row click navigates to `/topology?device_id={id}` and opens the panel
3. Map view (HT-008) — clicking a device in the location drawer does the same

The UX-Designer spec is the source of truth for layout, interactions, and accessibility.

## Acceptance Criteria
- Given a device node is selected on the canvas, when the panel opens, then I see sections in this order: Identity, Location, Tags, Custom Fields, Notes, Connections
- Given the panel is open, when I click on the device `name`, then the field becomes an inline text input with the current value pre-filled; Enter saves via `PATCH /api/devices/{id}`, Esc cancels
- Given I edit a field to an empty string, when I press Enter, then inline validation shows "Name is required" below the field and the save is blocked
- Given I edit `ip` to an invalid address, when I press Enter, then the domain IP validator (HT-002) rejects it and the error message is shown inline
- Given the device has tags, when the Tags section renders, then each tag is a coloured chip; clicking the "+" button opens a tag picker with all existing tags plus "Create new tag" (which delegates to HT-006's `POST /api/tags`)
- Given a tag is attached, when I click the `×` on its chip, then `DELETE /api/devices/{id}/tags/{tag_id}` fires and the chip disappears
- Given the device has custom fields, when the Custom Fields section renders, then each field is a `key: value` row with an edit pencil and a delete icon; clicking the pencil opens an inline edit for the value only
- Given I click "Add custom field", when the row appears, then I can enter a new key + value and save via `POST /api/devices/{id}/custom-fields` (HT-007)
- Given the device has connections, when the Connections section renders, then each connection shows "→ {neighbour-name} ({ConnectionType})" and clicking a neighbour navigates to that device, re-opening the panel for it
- Given the panel is open, when I press Esc, then the panel closes and the canvas selection is cleared
- Given the panel is open, when I navigate by Tab, then focus order is: close button → Identity fields → Location → Tags → Custom Fields → Notes → Connections links
- Given I open the panel on the map view or inventory list path (`/topology?device_id={id}`), when the page mounts, then the panel opens automatically with the device selected
- Given an edit fails with a 500 error, when the toast fires, then the field reverts to the last-known-good value and the error toast stays visible until dismissed

## Non-Goals (explicitly out of scope)
- Full-page device editor (panel is the only edit surface in v1)
- Reassigning the device to a different location from the panel (Phase 2 — v1 sends the user to Settings → Locations)
- Editing connection `type` or `label` from the panel's Connections section (v1 requires going to the edge on the canvas)
- Rich text / markdown in the notes field
- File attachments (manuals, receipts, photos)
- Version history / audit log of edits (Phase 2)

## Open Questions
None — the UX-Designer spec is the authoritative layout contract.

## Notes for Architect / Engineer
- Component at `src/ui/components/device_detail_panel.py` — reusable across topology, inventory, and map surfaces
- Data source: `GET /api/devices/{id}?include=tags,custom_fields,connections,location` — extend the existing device GET endpoint with an `include` query param if not already present; included nodes are opt-in to keep the list endpoint light
- Inline edit pattern: NiceGUI `ui.input` toggled in/out by click; Save on Enter + blur, Cancel on Esc
- All edits use existing endpoints: `PATCH /api/devices/{id}` (HT-002), `POST/DELETE /api/devices/{id}/tags/*` (HT-006), `POST/PATCH/DELETE /api/devices/{id}/custom-fields/*` (HT-007)
- Optimistic UI: apply the edit locally first, then call the API; on failure, revert to the prior value and show an error toast
- Accessibility: panel uses `role="complementary"` + `aria-label="Device details for {name}"`; open/close state announced via `aria-live="polite"`
- Dynamic updates (e.g. tag added) use `aria-live="polite"` region
- Keyboard-only path: user must be able to open panel (Enter on a focused canvas node), edit every inline field, and close it (Esc) without a mouse
- File size budget: keep `device_detail_panel.py` ≤ 250 lines; if needed extract sections into `src/ui/components/device_panel/` (tags_section.py, custom_fields_section.py, connections_section.py)
- The panel does NOT shrink the canvas — it overlays the right edge (per UX-Designer spec)
- RBAC: Readers see the panel in read-only mode (no pencil icons, no add/delete buttons); Contributors and Admins get full edit
- This story assumes HT-004, HT-005, HT-006, HT-007 are merged first — add that dependency note to the backlog
