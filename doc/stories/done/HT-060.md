# HT-060: Container Unconvert and Reparent Safe Server Coordination

**Status:** Done
**MoSCoW:** Must
**Kano:** Basic — deleting children without server confirmation or user acknowledgment is data loss
**Phase:** 1 (Hometower)
**Size:** L
**Shipped:** 13 April 2026

## Job-to-be-Done

As a Contributor, I want container operations (unconvert and reparent) to be coordinated with the server before DOM changes are applied, so that I never end up with a canvas that shows state the server doesn't agree with — or lose devices without a confirmation step.

## Context

Two Critical/High bugs share a structural gap: the canvas modifies the DOM before confirming server success, and neither operation has optimistic locking retry.

- **BUG-TOPO-007 (Critical):** "Unconvert container" removes all descendants and edges from the DOM immediately without first confirming successful server-side deletion. If the DELETE calls fail mid-sequence, the canvas loses nodes that still exist on the server. No confirmation dialog warns the user about which descendants will be deleted.
- **BUG-TOPO-006 (High):** Drag-reparent executes a `GET /api/devices/{id}` to retrieve the current version, then sends `PATCH /api/devices/{id}` with that version. Between the GET and PATCH, another client (or tab) may have already updated the device — the PATCH will get a 409 and the reparent silently fails with no retry and no user feedback. This is a TOCTOU race (Time-of-Check to Time-of-Use).

Both bugs are routed **Architect → Feature-Engineer** in `bug-report-12-04-26.2.md`. An Architect RFC is required before implementation begins.

**Source bugs:** BUG-TOPO-006, BUG-TOPO-007 (`bug-report-12-04-26.2.md`).

## Acceptance Criteria

- Given a container node has one or more children, when a Contributor clicks "Unconvert container", then a confirmation modal appears listing all direct child device names and the count of edges that will be permanently deleted from the server.
- Given the user clicks **Cancel** in the confirmation modal, when they return to the canvas, then the canvas is in the exact same state as before — no nodes or edges removed.
- Given the user confirms unconvert, when the server DELETE/PATCH calls execute for descendants, then: (a) all server calls must complete successfully before any node is removed from the DOM, and (b) if any server call fails, a toast error appears and the canvas is left unchanged.
- Given a node is drag-reparented onto a new parent container, when the PATCH fails with HTTP 409 (version conflict), then the client retries the PATCH up to 3 times by re-fetching the latest device version before each retry — not using the stale version from the initial GET.
- Given all 3 PATCH retries are exhausted, when the final 409 is received, then the node snaps back to its original parent on the canvas and a toast appears: *"Reparent failed — the device was modified by another user. Your change was not saved."*

## Non-Goals (explicitly out of scope)

- Undo/redo for unconvert operation (tracked as HT-032).
- Auto-cleanup of orphaned children when a container is deleted (a future inventory feature).
- Preventing concurrent reparent from two users acting on the same device simultaneously (real-time locking is Phase 2).

## Open Questions

1. **Unconvert deletion scope:** Should unconvert delete *all descendants recursively* (children, grandchildren) or only *direct children*, promoting grandchildren to the parent level? **Architect must decide before Feature-Engineer starts.**
2. **Reparent endpoint:** Should the PATCH use the existing `PATCH /api/devices/{id}` with `parent_id` in the body (and rely on the version field for optimistic locking), or should a dedicated endpoint `PATCH /api/devices/{id}/parent` be introduced to make the intent explicit? **Architect must decide.**
3. **Unconvert server call sequence:** Should the backend handle unconvert as a single transactional endpoint (`DELETE /api/devices/{id}?cascade=true`), or should the canvas issue individual DELETEs per child? A transactional endpoint is safer but needs a new API route. **Architect must decide.**

## UX Interaction Spec

**Unconvert confirmation modal:**
- Title: *"Delete container and its contents?"*
- Body: Lists up to 5 child device names with a "+N more" if over 5. Shows total edge count being removed.
- Buttons: `Cancel` (default focus, keyboard Escape) and `Delete {N} devices` (destructive red, requires deliberate click — Fitts's Law: separated from Cancel by ≥ 16px gap, not side-by-side).
- Norman's Constraint: Delete button label includes the count so the user must read it before confirming.

**Reparent conflict toast:**
- Placement: top-center, 6-second auto-dismiss.
- Visual: node on canvas snaps back to original parent position (animated, 200ms ease-out).

## Notes for Architect / Engineer

- BUG-TOPO-007 root: `canvas_container_events.py` calls DOM removal before server response — fix is to invert: collect all DELETEs, await all promises, then mutate DOM only in the `.then()`.
- BUG-TOPO-006 root: `canvas_container_events.py` GET-then-PATCH pattern — fix is to remove the GET entirely and rely on the version already stored in the canvas element's data (`node.data('version')`), retrying by re-fetching only on 409.
- If Architect chooses a new `cascade=true` endpoint, DevOps-Engineer will need a migration review to ensure the cascade DELETE is safe (no FK constraint violations for associated `connections`).
