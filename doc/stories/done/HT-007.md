# HT-007: Custom Fields (Key-Value Pairs per Device)

**Status:** Done
**MoSCoW:** Should
**Kano:** Delighter — homelabers each have their own idiosyncratic metadata (warranty date, serial number, noise profile). Giving them a free-form slot is what separates a toy from a real inventory.
**Phase:** 1 (Hometower)
**Size:** S (1-2 days)

## Job-to-be-Done
As a homelab owner, I want to attach arbitrary key-value pairs to any device (e.g. `serial: ABC123`, `warranty_expires: 2027-08-01`, `purchase_price: 450`) so that I can track metadata that the built-in fields don't cover.

## Context
The built-in Device fields (name, type, ip, mac, os, notes, location_id) cover the obvious cases. But every homelabber has idiosyncratic data they want to track: serial numbers, warranty expiry, purchase receipts, power draw in watts, firmware versions, ILO addresses, etc. Custom fields are the escape hatch.

The `CustomField` entity already exists in the data model (`device_id`, `key`, `value`). This story adds the CRUD and the display contract — the UX-Designer spec says "displayed as a compact key: value table — not a form by default", which HT-010 will implement.

Keys are unique per device (you can't have two `serial` entries on the same device), but global across devices (different devices may use different keys).

## Acceptance Criteria
- Given I am a Contributor and a device exists, when I `POST /api/devices/{id}/custom-fields` with `{key: "serial", value: "ABC123"}`, then the field is created
- Given a device already has a `serial` field, when I `POST` another `serial` on the same device, then I receive a 409 Conflict: "Key already exists on this device"
- Given a device has a `serial` field, when I `PATCH /api/devices/{id}/custom-fields/{field_id}` with `{value: "XYZ789"}`, then the value is updated but the key remains
- Given I `POST` with `{key: "", value: "abc"}`, then I receive a 400 error: "Key cannot be empty"
- Given I `POST` with a key longer than 64 chars or a value longer than 1024 chars, then I receive a 400 error with the specific limit
- Given a custom field exists, when I `DELETE /api/devices/{id}/custom-fields/{field_id}`, then it is removed and returns 204
- Given I `GET /api/devices/{id}`, then the response includes a `custom_fields` array of `{id, key, value}` objects
- Given a device is deleted, when the deletion commits, then all its custom fields are deleted (cascade)
- Given I `POST` a value containing only whitespace, then the whitespace is preserved (trimming is a display concern, not a storage concern)

## Non-Goals (explicitly out of scope)
- Typed custom fields (date picker, number, boolean) — v1 is string-only
- Cross-device custom field templates (e.g. "every server needs a serial field")
- Validation rules per key (regex, ranges) — Phase 2
- Searching/filtering by custom field value in the inventory list — Phase 2 (HT-020 covers built-in field search only)
- Bulk custom-field editing
- Rich text or markdown in values — plain strings only

## Open Questions
None — keys are strings, values are strings, the limits are set.

## Notes for Architect / Engineer
- SQLModel at `src/models/custom_field.py`: `CustomField(id, device_id FK, key, value, created_at, updated_at)`
- Composite unique index on `(device_id, LOWER(key))` — case-insensitive per-device uniqueness
- Domain pure function `normalize_custom_field_key(key: str) -> str` in `src/domain/inventory.py` — strip + lowercase for uniqueness comparison, preserve original casing for display
- Pydantic validators: `key` length 1..64 (after strip), `value` length 0..1024
- Repository at `src/repositories/custom_field_repository.py`: `create`, `get_by_id`, `get_by_device`, `update`, `delete`
- Service at `src/services/custom_field_service.py` — enforces per-device key uniqueness
- New router section in `src/api/routers/devices.py`: sub-routes under `/api/devices/{id}/custom-fields` to keep ownership clear (not a separate top-level router)
- Extend `DeviceRead` response schema to include `custom_fields: List[CustomFieldRead]`
- Alembic migration: new `custom_fields` table with `ON DELETE CASCADE` on the device FK
- No standalone UI — rendering lives in HT-010 (device detail panel "Custom Fields" section)
- RBAC: create/update/delete require `Role.Contributor` or higher
- Do NOT add a general-purpose "custom fields" catalogue — each device's fields are independent
