# HT-006: Tag System for Devices

**Status:** Done
**MoSCoW:** Should
**Kano:** Performance — more tagging = faster filtering; also a Delighter when colour-coded tags cluster on the canvas
**Phase:** 1 (Hometower)
**Size:** S (1-2 days)

## Job-to-be-Done
As a homelab owner, I want to attach coloured labels to my devices (e.g. "production", "noisy", "test-bed", "k3s-cluster") so that I can group and filter infrastructure by intent rather than just by type.

## Context
Tags are a cross-cutting classification system that lets the inventory view (HT-009) and filter bar group devices by user-defined criteria. Each tag has a name and a user-picked colour. The `DeviceTag` join model has already been committed to the data model in `AGENTS.md`.

Tags are globally scoped (v1 is single-workspace). Tag name is unique (case-insensitive).

## Acceptance Criteria
- Given I am a Contributor, when I `POST /api/tags` with `{name: "production", color: "#22c55e"}`, then the tag is created and returned
- Given a tag named "Production" exists, when I `POST /api/tags` with `{name: "production"}`, then I receive a 409 Conflict (case-insensitive uniqueness)
- Given I `POST /api/tags` with `{name: "", color: "#ff0000"}`, then I receive a 400 error: "Tag name cannot be empty"
- Given I `POST /api/tags` with `{name: "prod", color: "not-a-color"}`, then I receive a 400 error: "Color must be a valid hex code"
- Given a tag and a device exist, when I `POST /api/devices/{device_id}/tags` with `{tag_id}`, then the tag is attached and the device's tag list includes it
- Given a tag is already attached to a device, when I re-attach the same tag, then the operation is idempotent (no error, no duplicate)
- Given a tag is attached to a device, when I `DELETE /api/devices/{device_id}/tags/{tag_id}`, then the tag is detached but the tag itself still exists
- Given a tag exists on N devices, when I `DELETE /api/tags/{id}`, then the tag and all its device associations are removed (cascade)
- Given I `GET /api/tags`, then I receive every tag with a `device_count` field showing how many devices carry it
- Given I `GET /api/devices/{id}`, then the response includes a `tags` array with each attached tag's id, name, and colour

## Non-Goals (explicitly out of scope)
- Hierarchical tags or tag groups (flat namespace only in v1)
- Auto-tagging rules (e.g. "all servers get a 'server' tag")
- Tag icons — colour is the only visual differentiator
- Tag-based RBAC (Phase 2 — tags do not gate permissions in v1)
- Bulk tag application across multiple devices (HT-009 filter can help, but multi-select bulk-tag is Phase 2)

## Open Questions
None — the data model is frozen and uniqueness is defined as case-insensitive.

## Notes for Architect / Engineer
- SQLModel at `src/models/tag.py`: `Tag(id, name, color, created_at)` and `DeviceTag(device_id, tag_id)` as an explicit join model
- Unique index on `LOWER(name)` in Alembic migration — enforces case-insensitive uniqueness at DB level
- Pydantic validator for `color`: must match `^#[0-9a-fA-F]{6}$`
- Domain pure function `normalize_tag_name(name: str) -> str` in `src/domain/inventory.py` — lowercases + strips whitespace
- Repository at `src/repositories/tag_repository.py`: `create`, `get_by_id`, `get_all_with_counts`, `delete`, `attach_to_device`, `detach_from_device`, `get_by_device`
- Service at `src/services/tag_service.py` — orchestrates uniqueness check and attach idempotency
- Router at `src/api/routers/tags.py` — Pydantic `TagCreate`, `TagRead`, `TagReadWithCount`
- Extend `src/api/routers/devices.py` with `POST /api/devices/{id}/tags` and `DELETE /api/devices/{id}/tags/{tag_id}`
- Extend `DeviceRead` response schema to include the `tags` array (uses the existing device GET route — no new endpoint)
- No new UI page in this story — HT-009 (inventory filter bar) and HT-010 (device detail panel) both consume tags
- RBAC: create/update/delete/attach/detach require `Role.Contributor` or higher
- Cascade on tag delete handled in migration via `ON DELETE CASCADE` for the `device_tags` table
