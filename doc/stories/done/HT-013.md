# HT-013: Import from JSON

**Status:** Completed
**MoSCoW:** Should
**Kano:** Performance — restoring from backup is rare but high-stakes. Fast, reliable import builds trust.
**Phase:** 1 (Hometower)
**Size:** M (3-4 days)

## Job-to-be-Done
As a homelab owner, I want to import a previously exported JSON file so that I can restore my inventory on a fresh instance, migrate between machines, or recover from data loss.

## Context
HT-012 defines the export format. This story consumes it. Import is destructive-by-design in v1: it replaces the current inventory. A "merge" mode (skip existing, update conflicts) is complex and deferred to Phase 2. The user is warned before proceeding.

## Acceptance Criteria
- Given I am an Admin, when I `POST /api/import` with a valid HT-012 JSON file, then all entities are created in dependency order (locations → devices → connections → tags → device-tags → custom fields → networks → device-networks → services → diagram layouts) and I receive a summary: `{"devices": 42, "connections": 15, ...}`
- Given the import file has `version: "1.0"`, when the import runs, then it is accepted
- Given the import file has `version: "2.0"` (unknown), when the import runs, then it returns HTTP 400: "Unsupported export version: 2.0"
- Given the import file is malformed JSON, when the upload fires, then I receive HTTP 400: "Invalid JSON"
- Given the import file passes schema validation but an entity violates a constraint (e.g., duplicate MAC), when the insert fails, then the entire import rolls back and I receive HTTP 422 with the specific validation error and entity reference
- Given I am a Contributor or Reader, when I `POST /api/import`, then I receive HTTP 403 (Admin only)
- Given the current instance has existing data, when I trigger import, then a confirmation dialog warns: "This will replace all existing data. Export first if needed." — the API requires a `confirm=true` query param
- Given the import succeeds, when I navigate to the topology canvas, then all imported devices and connections render correctly
- Given the import file references UUIDs, when the import runs, then original UUIDs are preserved (not regenerated) so external references remain stable
- Given the JSON file exceeds 50MB, when the upload fires, then I receive HTTP 413: "Import file too large (max 50MB)"

## Non-Goals (explicitly out of scope)
- Merge/upsert mode (skip existing, update conflicts) — Phase 2
- Import from other tools (Netbox, LibreNMS, CSV) — Phase 2
- Partial import (e.g., "only import devices, skip connections")
- Dry-run / preview mode before committing
- Import of user accounts (security risk — users are managed separately)
- Progress streaming for large imports (v1 is synchronous)

## Open Questions
None — replace-all semantics and Admin-only access are confirmed.

## Notes for Architect / Engineer
- Router: `POST /api/import` in `src/api/routers/import_export.py` (or extend `export.py` → rename to `import_export.py`)
- Service: `src/services/import_service.py` — runs the full import in a single DB transaction; any failure rolls back everything
- Validate the upload against `ExportSchema` (from HT-012) before touching the database
- Dependency order: truncate all tables in reverse dependency order, then insert in forward order — use `TRUNCATE ... CASCADE` within the transaction
- File size limit: enforce `50MB` via FastAPI's `UploadFile` with a size check before parsing
- Preserve original UUIDs: insert with explicit `id` values from the JSON, not auto-generated
- RBAC: `require_role(Role.Admin)` — only Admins can perform destructive imports
- UI: add "Import JSON" button in Settings page with file picker + confirmation modal
- Security: validate that the JSON does not contain `password_hash` fields — if present, ignore them silently
