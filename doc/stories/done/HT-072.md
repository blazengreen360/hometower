# HT-072: Replace Layout Management with Topology History

**Status:** Done
**MoSCoW:** Must
**Kano:** Basic — homelabbers should not have to manage a second abstraction like layouts or views just to save meaningful checkpoints of a topology.
**Phase:** 1 (Hometower)
**Size:** M (2-3 days)

## Job-to-be-Done
As a homelab owner, I want to save explicit topology versions into a History panel so that I can return to meaningful checkpoints without managing parallel layouts manually.

## Context
The 14 April 2026 design session closed the core information-architecture question:

- **Workspace** = the homelab container
- **Topology** = a concern-specific diagram
- **History** = automatic saved versions of that topology, visible only when needed

This replaces the remaining user-facing `Layout` / `View` language from HT-029 and related flows. A topology is the thing the user edits. History is a secondary surface for explicit checkpoints. It behaves more like Confluence page history than a user-managed list of alternate canvases.

Explicit **Save Version** creates an immutable history entry. Restoring an older entry creates a new latest version rather than mutating or overwriting the past.

## Acceptance Criteria
- Given I am on a topology canvas as a Contributor or Admin, when I click **Save Version**, then a new immutable history entry is created for that topology and it becomes the latest version
- Given I open **History** for a topology, when the panel loads, then I see saved versions listed newest-first with the current version clearly marked
- Given I restore an older history entry, when the restore completes, then the topology canvas reflects that older state and a new latest history entry is created while the original restored entry remains unchanged
- Given I am a Reader, when I open History, then I can inspect the saved versions but cannot trigger **Save Version** or **Restore**
- Given a topology has no saved history beyond its current working state, when I open History, then I see an empty-state prompt explaining that **Save Version** creates the first checkpoint
- Given the topology toolbar currently exposes layout-oriented actions, when this story lands, then the primary user-facing actions become **Save Version** and **History** and layout/view terminology is removed from the main canvas workflow

## Non-Goals (explicitly out of scope)
- Branching history trees or named release channels
- Visual diffing between history entries
- Required version notes or commit-style messages
- Automatic migration of every legacy HT-029 multi-layout edge case into the new model

## Open Questions
None.

## UX Interaction Spec
- **Placement:** `Save Version` is the primary canvas action in the top toolbar near the topology title. `History` is a secondary action adjacent to it.
- **History panel:** right-side drawer, collapsible, approximately 360-420px wide on desktop and full-width sheet on mobile.
- **Interaction triggers:** click `Save Version` to create a checkpoint; click `History` to open the drawer; click a history row's `Restore` action to recover that version.
- **State transitions:** default toolbar state -> saving spinner on `Save Version` -> success toast + new history row -> restored state banner after a restore.
- **Edge-case constraints:** Readers see the drawer in read-only mode; empty history shows guidance rather than a blank list; restore never rewrites the original entry.
- **Fitts's Law justification:** `Save Version` is a frequent, high-value action and must be large and close to the canvas title/context. `Restore` is deliberate and lower-frequency, so it lives inside the history row rather than as a large always-visible destructive-style control.

## Notes for Architect / Engineer
- Keep `DiagramLayout` or equivalent storage internals if useful, but the user-facing copy must become **Topology**, **History**, and **Version** rather than **Layout** or **View**.
- Restore must be append-only: the restored content becomes a new latest version, preserving the audit trail.
- Reuse the existing direct-topology entry model from HT-057. History is a secondary affordance on the topology page, not a table the user navigates through first.
- Legacy named layouts from HT-029 may remain behind compatibility plumbing temporarily, but they should no longer drive the primary canvas UX after this story lands.
