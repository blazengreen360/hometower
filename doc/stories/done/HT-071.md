# HT-071: Friendly Validation Feedback Across Settings Forms

**Status:** Done
**MoSCoW:** Should
**Kano:** Basic — when forms reject user input, the application must explain the problem in human terms. Raw escaped backend payloads and silent invalid submissions feel broken.
**Phase:** 1 (Hometower)
**Size:** M (2-3 days)

## Job-to-be-Done
As an admin managing users, locations, and my own account, I want settings forms to show clear inline validation messages so that I can correct mistakes immediately without guessing what failed.

## Context
The user simulation on 14 April 2026 found three related feedback defects across settings surfaces:
- **Users** create dialog can render an escaped backend validation payload instead of human-friendly messages
- **Locations** add dialog can render the same kind of escaped backend payload for empty-name validation
- **Profile** password-change form provides no visible validation feedback for an invalid submit path

These are all part of the same product problem: validation behavior is inconsistent across settings pages, despite HT-055 already establishing better dialog feedback patterns elsewhere.

## Acceptance Criteria

### Users dialog
- Given I open **Settings -> Users -> Add User**, when I submit with missing required fields, then I see clear human-readable validation messages instead of raw JSON-like backend payloads
- Given the backend rejects the request with validation errors, when the dialog stays open, then the message is concise, non-escaped, and actionable
- Given I correct the invalid field, when I resubmit, then the stale error message clears appropriately

### Locations dialog
- Given I open **Settings -> Locations -> Add Location**, when I submit with an empty name, then I see a friendly inline validation message such as `Name is required`
- Given validation fails, when the dialog remains open, then no escaped backend payload array is rendered to the user
- Given I fix the input and save again, when the request succeeds, then the dialog closes normally and success behavior is unchanged

### Profile password form
- Given I open **Settings -> Profile**, when I submit a new password that is too short, mismatched, or otherwise invalid, then the page shows visible validation feedback in the form
- Given the current password is incorrect, when the backend rejects the request, then the user sees a clear error message explaining that the current password is wrong
- Given the form submission fails, when the page remains visible, then the user does not have to infer failure from the absence of change

### Consistency and safety
- Given any of these forms fail validation, when the UI displays the message, then it never exposes raw backend validation structures or escaped entity blobs
- Given a network or server error occurs, when the form request fails, then the user sees a concise non-sensitive failure message rather than a stack-shaped payload
- Given the Networks modal is already using friendly validation, when this story lands, then Users, Locations, and Profile feel consistent with that standard

### Regression protection
- Given the relevant execution/unit tests run, when invalid form submissions are exercised, then the UI messages are human-readable and stable across Users, Locations, and Profile flows

## Non-Goals (explicitly out of scope)
- New password-policy rules beyond what the backend already enforces
- Full form redesigns or layout changes
- Translating every backend validation error into field-by-field localization keys

## Notes for Architect / Engineer
- Reuse the validation-feedback patterns from HT-055 rather than inventing a second pattern family
- Likely touch points: `src/ui/pages/settings_users.py`, `src/ui/pages/settings_locations.py`, and `src/ui/pages/settings_profile.py` (or their equivalent modules)
- Prefer translating known validation cases into clean UX copy close to the form layer; do not dump backend payloads straight into the DOM
