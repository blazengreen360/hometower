# HT-059: Draft Publish Atomic Rollback and ID Safety

**Status:** Done
**MoSCoW:** Must
**Kano:** Basic — data corruption (orphaned edges, invisible nodes) causes severe dissatisfaction
**Phase:** 1 (Hometower)
**Size:** M
**Shipped:** 13 April 2026

## Job-to-be-Done

As a Contributor, I want to publish draft devices with confidence that either the publish fully succeeds or the canvas rolls back to exactly its prior state, so that my diagram is never left corrupted with orphaned edges or invisible nodes.

## Context

Seven related bugs all threaten the integrity of the draft→publish flow:

- **IMPL-2.1 (Critical):** Draft nodes use `crypto.randomUUID()` for their client-side ID with no prefix. If the server has already persisted a device with the same UUID, the canvas holds two references to that ID — draft and published. On reload the saved layout's reference becomes orphaned.
- **IMPL-3.1 (High):** `window._htDraftId()` is referenced in `canvas_events.py` but may be undefined if the defining script hasn't executed, silently creating a node with `id: undefined`.
- **BUG-TOPO-004 (Critical):** Publish rollback re-adds edges from `connectedEdges` without checking for existing duplicate edges or verifying `cy.add()` succeeded.
- **BUG-TOPO-005 (High):** Concurrent draft promotions in two tabs can cause the second promote to attempt duplicate edge adds for edges the first tab already promoted.
- **BUG-TOPO-011 (High):** When the API is unreachable during publish, rollback may fail to restore edges properly (the draft node is re-added but edge restoration is conditional on an error path that may have already mutated edge data).
- **BUG-TOPO-018 (Medium):** A draft edge connecting a draft node to a published device is not promoted to a real persisted edge after publish — `_htPromoteConnections` ignores edges still marked `draft_edge`.
- **IMPL-8.1 (Medium):** The rollback path calls `cy.add()` but never verifies the result — a silent failure leaves the graph corrupted.

**Source bugs:** BUG-TOPO-004, BUG-TOPO-005, BUG-TOPO-011, BUG-TOPO-018 (`bug-report-12-04-26.2.md`); IMPL-2.1, IMPL-3.1, IMPL-8.1 (`CANVAS_IMPLEMENTATION_BUG_REPORT_20260413.md`).

## Acceptance Criteria

- Given `window._htDraftId()` is called anywhere in the canvas JS, when the function runs, then it always returns a string with the prefix `draft-` (e.g., `draft-<uuid4>`) and never returns `undefined` — a `window._htDraftId = window._htDraftId || function() { return 'draft-' + crypto.randomUUID(); }` guard prevents silent node creation with `id: undefined`.
- Given a server device has UUID `abc-123`, when a new draft is created on the same canvas, then the draft's ID cannot equal `abc-123` because the `draft-` prefix structurally prevents collision with any server-assigned UUID.
- Given a publish flow completes and the server returns a new UUID, when the canvas verifies `cy.getElementById(newId).length === 1`, then if verification fails: (a) rollback re-adds the original draft node, (b) rollback re-adds connected edges **only if they don't already exist** (`cy.getElementById(eId).length === 0` check), (c) if rollback's own `cy.add()` returns a collection of length ≠ 1, then a critical toast fires: *"Graph state corrupted. Please reload immediately."*
- Given a draft edge (`draft-edge-` prefix) connects a draft node to a published device, when the draft node is published, then `_htPromoteConnections` includes that edge in its promotion sweep — it is created as a real connection via the API, not silently ignored.
- Given two browser tabs simultaneously publish separate drafts that share an edge, when the second tab runs `_htPromoteConnections`, then it skips any connection ID already present on the canvas (no duplicate edge creation).
- Given a draft publish fails because the API returns 5xx, when the publish error path runs, then the canvas is restored to the exact pre-publish state: draft node present, all connected edges present, `draft-error` class applied — no edges missing from the canvas.

## Non-Goals (explicitly out of scope)

- Multi-user real-time draft coordination / operational transform (Phase 2).
- Server-side draft state persistence (drafts remain client-only until published).
- Preventing the user from publishing two conflicting drafts simultaneously (UX warning only, not a lock).

## UX Interaction Spec

**Publish failure toast:**
- Placement: top-center, persistent.
- Text: *"Publish failed — your draft has been kept. Try again or reload."*
- The draft node returns to `draft-error` visual state (red outline) to signal the failure location.

**Corrupt graph critical toast:**
- Full-width banner (not a corner toast) — indicates page reload required.
- Text: *"Graph may be corrupted. Please reload the page to restore from last saved state."*
- Primary action: Reload button.

## Notes for Architect / Engineer

- The `draft-` prefix fix must be applied in `canvas_draft.py` where `_htDraftId` is defined AND `canvas_events.py` where it is called — use the guard pattern so both callers are safe even if load order varies.
- `_htPromoteConnections` filtering: before creating each connection via the API, check `cy.getElementById(edge.data.id).length === 0`. If the graph already has that edge (promoted by another tab), skip the API call.
- `cy.add()` return value: the Cytoscape API returns a Collection — check `.length` rather than truthiness.
- The draft edge promotion gap (BUG-TOPO-018) is in `canvas_draft_publish.py` — the filter that selects edges to promote should use `_htIsDraftEdge()` (see HT-065 for full `_htIsDraftEdge` robustness fix; here, the fix only needs to include `draft-edge-` prefixed edges in the promote set, which works even if `_htIsDraftEdge` is not yet fully correct).
