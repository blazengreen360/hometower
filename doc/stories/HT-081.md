# HT-081: Data Table Enhancements & Pagination

**Status:** Ready
**MoSCoW:** Must
**Kano:** Basic — lists that scale without crashing or requiring excessive scrolling are a table stakes expectation.
**Phase:** 1 (Hometower)
**Size:** M

## Job-to-be-Done

As an administrator or active homelabber with many environments, I want my tables (Workspaces, Topologies, IAM/Users) to be paginated, searchable, and uniformly presented so that I can easily navigate large datasets without overwhelming the UI.

## Context

The current views for Workspaces and Topologies have no pagination, causing performance and usability issues in larger environments. The existing IAM view (Admin Users) also lacks a proper list view, rendering it incongruous with the rest of the application.

Design decision resolved in session: **Standard Data Table** (like Inventory). The IAM/Users view will be updated to perfectly match the Inventory table pattern (searchable, sortable, paginated). 

## Acceptance Criteria

- Given the `/workspaces` page, when rendering the list of workspaces, then it displays as a modern, paginated NiceGUI table (`ui.table`), limiting rows per page (e.g., 20) with standard pagination controls.
- Given the Topologies view (within a workspace or standalone list), when rendering topologies, then it similarly uses a paginated data table structure.
- Given the `/admin/users` (IAM) page, when an Admin accesses the page, then the user list is presented in a Standard Data Table component with columns for Username, Email, Role, Last Active, and Actions.
- Given any data table in the app, when a user clicks a column header (e.g. "Name" or "Date"), then the table sorts the data correctly ascending/descending.
- Given the IAM view table, when a user searches by username or email, then the table dynamically filters matching rows without requiring a page reload.

## Non-Goals (explicitly out of scope)

- Adding bulk operations to the IAM/Users table (e.g., "Delete 10 users at once"). Single-row action buttons are sufficient.
- Server-side pagination mechanics for Phase 1. Client-side pagination (sending the full array to `ui.table` and having Quasar handle pages) is sufficient for current typical row counts (10–1000).

## Business Invariants

- Only Admins can modify users on the IAM table; UI action buttons (Edit, Delete) must be disabled or hidden if verifying the JWT role on the backend fails, although the route itself requires Admin anyway.
- The `ui.table` component must be styled consistently with the theme engine variables (transparent backgrounds, flat borders) defined in HT-080.
- All timestamps in tables must display in human-readable locale formats, continuing the convention established in HT-054.

## UX Interaction Spec

- **Table Design**: Use a flat, borderless or single-border outline style (`flat bordered`) rather than elevated drop shadows.
- **Search Bar**: Positioned at the top-right above the table, full width on mobile, max-width `240px` on desktop.
- **Pagination Controls**: Standard Quasar pagination at the bottom-right of the table with a "Rows per page" dropdown.
- **Action Column**: Fixed width on the right containing flat, dense icon buttons (`edit`, `delete`) with tooltips.

## Notes for Architect / Engineer

- Use NiceGUI's `ui.table` which natively wraps Quasar's `q-table`.
- Set pagination defaults: `pagination={'rowsPerPage': 25, 'sortBy': 'name'}`.
- Wire up a `ui.input()` to the table's `filter` property if building custom search input outside of the Quasar header slot.
- For IAM / Users (`src/ui/pages/admin_users.py` or similar), replace whatever current layout exists with a direct clone of the methodology used in `inventory.py`. Ensure password reset and user deletion modals attach correctly to action buttons.
