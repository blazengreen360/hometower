# HT-023: Services

**Status:** Ready
**MoSCoW:** Must
**Kano:** Performance — homelabbers inventory infrastructure to track what it *does*. A server with no services listed is just a box. Services answer "where is my Plex?" which is the real question.
**Phase:** 1 (Hometower)
**Size:** M (3-4 days)

## Job-to-be-Done
As a homelab owner, I want to record which services run on each device (name, port, URL, protocol, status) so that when something goes down I know exactly where it lives, and when I'm planning changes I can see what depends on what.

## Context
Nobody inventories a homelab to track hardware. They track it to know where Plex runs, which box hosts Pi-hole, what URL reaches Nextcloud, and what breaks if the Docker host reboots. Services are the **purpose layer** — they answer "why does this device exist?"

A Service belongs to exactly one Device (the device it runs on). Services can have dependencies on other services (e.g., Nextcloud depends on MariaDB), which creates a dependency graph overlaid on the topology.

Combined with HT-021 (containers), this enables the full picture: a Docker host (container device) holds Docker containers (child devices), each running a service (Plex, Pi-hole, etc.) with a port and URL.

## Acceptance Criteria

### Data model
- Given I `POST /api/devices/{device_id}/services` with `{name: "Plex", port: 32400, protocol: "https", url: "https://plex.home.lan", status: "running", notes: "Media server"}`, then the service is created and linked to the device
- Given I `POST` with `port: 70000`, then I receive HTTP 400: "Port must be between 1 and 65535"
- Given I `POST` with `protocol: "fax"`, then I receive HTTP 400 — protocol must be one of: `http`, `https`, `tcp`, `udp`, `other`
- Given a device already has a service named "Plex" (case-insensitive), when I create another "plex" on the same device, then I receive HTTP 409: "Service already exists on this device"
- Given I `GET /api/devices/{id}?include=services`, then the response includes a `services` array
- Given I `GET /api/services`, then I receive a flat list of all services across all devices, each including `device_id`, `device_name`
- Given I `GET /api/services?q=plex`, then the list is filtered by service name (substring, case-insensitive)
- Given I `PATCH /api/services/{id}` with `{status: "stopped"}`, then the status is updated
- Given I `DELETE /api/services/{id}`, then the service is removed
- Given a device is deleted (HT-002), when the deletion commits, then all its services are cascade-deleted

### Service dependencies
- Given service A (Nextcloud) and service B (MariaDB) exist, when I `POST /api/services/{a_id}/dependencies` with `{depends_on: b_id}`, then the dependency is recorded
- Given I query `GET /api/services/{a_id}?include=dependencies`, then the response includes `depends_on: [{id, name, device_name}]` and `depended_by: [{id, name, device_name}]`
- Given I try to create a circular dependency (A → B → A), then I receive HTTP 400: "Circular dependency detected"
- Given I delete a service that other services depend on, then the dependencies are cascade-deleted (the dependent services remain, just lose the link)

### Canvas integration
- Given a device has services, when I hover over the device node on the canvas, then a tooltip shows the service names and their status (green dot = running, red dot = stopped, grey dot = unknown)
- Given I select a device node, when the detail panel opens (HT-010), then the "Services" section lists each service with name, port, URL (clickable link), protocol, and status badge

### Inventory integration
- Given I am on the inventory list (HT-009), when devices have services, then the "Services" column shows a count badge (e.g., "5 services")
- Given I search `service:plex` (HT-020), then the device hosting Plex appears in results

## Non-Goals (explicitly out of scope)
- Service health checking (ping, HTTP probe) — Phase 2
- Service auto-discovery from Docker API or Proxmox — Phase 2 (LT-001, LT-002)
- Service configuration management (environment variables, volumes)
- Service-to-service connection rendering as edges on the canvas (dependencies are metadata, not visual edges in v1 — could be a future Delighter)
- Service versioning or changelog
- Service groups or categories
- Uptime tracking or monitoring dashboards

## Open Questions
None — the entity, dependency model, and canvas tooltip behavior are confirmed.

## Notes for Architect / Engineer

### Data model
- `src/models/service.py`: `Service(id, device_id FK, name, port: int | None, protocol: ServiceProtocol, url: str | None, status: ServiceStatus, notes: str | None, created_at, updated_at)`
- `src/models/service_dependency.py`: `ServiceDependency(service_id FK, depends_on_id FK)` — composite PK, both FKs to `services.id`
- Add enums to `src/models/types.py`: `ServiceProtocol(http, https, tcp, udp, other)`, `ServiceStatus(running, stopped, unknown)`
- Domain: `src/domain/services.py` — `validate_port(port: int)`, `validate_no_dependency_cycle(service_id, depends_on_id, session)`

### Canvas
- Hover tooltip: extend the existing Cytoscape `tippy` or native tooltip to show services — fetch via `GET /api/devices/{id}?include=services` on first hover, cache client-side
- Status indicator: small colored dots next to the device node (or inside the tooltip) — green/red/grey

### API
- Router: `src/api/routers/services.py` — `GET /api/services` (list all), `POST/GET/PATCH/DELETE` under `/api/devices/{id}/services/` and `/api/services/{id}`
- Dependency sub-routes: `POST /api/services/{id}/dependencies`, `DELETE /api/services/{id}/dependencies/{dep_id}`, `GET /api/services/{id}?include=dependencies`
- Service: `src/services/service_service.py` — orchestrates CRUD + cycle detection
- Repository: `src/repositories/service_repository.py`
- RBAC: create/update/delete require Contributor+; read for all authenticated users
- Cascade: `ON DELETE CASCADE` from `devices` to `services`, and from `services` to `service_dependencies`

### Unique constraint
- Composite unique index on `(device_id, LOWER(name))` — same pattern as custom fields (HT-007)
