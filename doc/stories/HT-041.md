# HT-041: Device Duplication (Clone)

**Status:** Ready
**MoSCoW:** Could
**Kano:** Delighter — nobody expects this, but once available it saves minutes per device when setting up a new rack of similar machines. Small effort, outsized satisfaction.
**Phase:** 1 (Hometower)
**Size:** XS (half day)

## Job-to-be-Done
As a homelab owner, I want to duplicate an existing device so that when I add similar hardware (e.g. three identical Raspberry Pis, a second NAS), I don't have to re-enter type, OS, tags, custom fields, and location from scratch.

## Context
Power users building out their homelab often add clusters of similar devices. Creating each one from scratch means re-selecting type, OS, location, re-adding the same tags and custom fields. A "Duplicate" action on the device detail panel would copy the device's properties into a new device with `name = "{original name} (copy)"`.

## Acceptance Criteria

### Trigger
- Given I have a device's detail panel open (HT-010), when I am a Contributor or Admin, then a "Duplicate" button (or icon) is visible in the panel header/toolbar
- Given I am a Reader, when I view the detail panel, then no Duplicate button is shown

### Duplication behaviour
- Given I click "Duplicate", when the operation executes, then a new device is created via `POST /api/devices` with the following fields copied from the source:
  - `type` — copied exactly
  - `os` — copied exactly
  - `notes` — copied exactly
  - `location_id` — copied exactly
  - `status` — copied exactly (if HT-039 is shipped; else skip)
- Given the new device is created, when I see its name, then it is `"{original name} (copy)"` — if that name already exists, append a number: `"(copy 2)"`, `"(copy 3)"`, etc.
- Given the original device has tags, when the duplicate is created, then all the same tags are associated with the new device
- Given the original device has custom fields, when the duplicate is created, then all custom field key-value pairs are copied to the new device

### What is NOT copied
- `id` — new UUID generated
- `ip` — set to `null` (IPs are unique per device)
- `mac` — set to `null` (MACs are unique per device)
- `created_at` / `updated_at` — set to current timestamp
- Canvas position — the new device is not placed on the topology canvas (user drags it on manually)
- Connections — no connections are duplicated

### Feedback
- Given the duplication succeeds, when the API responds, then a success toast shows: "Device duplicated: {new name}"
- Given the duplication succeeds, when the toast shows, then the detail panel switches to show the newly created device
- Given the duplication fails, when the API responds, then an error toast shows the reason

## Non-Goals (explicitly out of scope)
- Batch duplication (duplicate multiple devices at once)
- "Template" devices that are not part of the inventory
- Duplicating connections along with the device
- Placing the duplicate automatically on the canvas

## Open Questions
None.

## Notes for Architect / Engineer
- **Backend**: This is a client-orchestrated operation — no dedicated "duplicate" endpoint needed. The UI reads the source device, constructs a `DeviceCreate` payload with the copied fields, then calls `POST /api/devices`. Follow up with `POST /api/device-tags` and `POST /api/custom-fields` for each tag and field.
- **Name collision**: Domain logic (`src/domain/devices.py`) should have a helper `generate_copy_name(original_name, existing_names) -> str` that returns the next available `"(copy N)"` suffix. This is a pure function, independently testable.
