# HT-086: Deep Execution Environments (UML-Style Deployment Modeling)

**Status:** on-hold
**MoSCoW:** Could -> Should (Killer Feature Candidate)
**Kano:** Delighter — transforms Hometower from a simple drag-and-drop physical map into a rigorous, semantic architecture tool (Infrastructure-as-UML).
**Phase:** 1 (Hometower)
**Size:** L

## Job-to-be-Done

As a homelabber managing complex virtualization stacks, I want to visually map services, containers, and virtual machines inside their physical hosts using a strict UML Deployment Diagram paradigm, so that the diagram accurately models the exact execution environment and dependencies of my workloads.

## Context

Currently, the canvas allows users to create generic "Containers" (HT-021) and freely drag devices into them. While this solves simple visual grouping, a real homelab needs semantic boundaries: a Docker container runs *inside* a VM, which runs *on* a Proxmox Host, which sits *in* a Rack. 

Applying UML Deployment Diagram principles to Hometower transforms the canvas from a drawing board into a semantic model where physical nodes, execution environments (VMs/LXCs), and software artifacts (services) are strictly validated and visually hierarchical.

## Acceptance Criteria

Feature: UML-Style Deployment Modeling on Canvas

  Scenario: Hierarchical container types
    Given the user opens the Device Tools palette
    When they review the options for containers
    Then there are distinct, semantically typed execution environments available: "Rack", "Server/Hypervisor", "Virtual Machine", and "Docker/Pod/LXC"
    And each environment type has distinct UML-inspired visual styling (e.g., 3D box for Hardware node, standard box for execution environment)

  Scenario: Strict nesting validation
    Given a user is dragging a new or existing node into a container
    When they attempt an invalid nesting (e.g., dropping a "Server" inside a "Docker Container")
    Then the drop is rejected
    And a toast notification explains the invalid UML deployment constraint: "A physical server cannot be deployed inside a container."
    And the node returns to its previous position

  Scenario: Valid deployment instantiation
    Given a user drags a "Docker Container" device type from the palette
    When they drop it directly inside a "Virtual Machine" boundary
    Then the new device is instantly created and parented to the VM
    And the VM automatically expands to fit if necessary (HT-077 floor rules apply)

  Scenario: Layered visibility toggles
    Given a deeply nested topology (Service -> Docker -> VM -> Server -> Rack)
    When the user clicks the "View Layers" control on the canvas toolbar
    Then they can toggle visibility of specific execution layers (e.g., "Hide all software services", "Show only physical hardware")
    And the canvas dynamically collapses child nodes or greys out environments based on the active layer view

  Scenario: Service deployment mapping (Software Artifacts)
    Given the user creates a "Service" (e.g., Plex, Nextcloud)
    When they drag the Service into an execution environment (like a Docker node or VM)
    Then the Service is visually represented as an artifact bound to that execution environment, mimicking UML artifact deployment

## Non-Goals (explicitly out of scope)

- Modeling purely abstract classes (this remains a map of *actual* deployed inventory, just modeled strictly).
- Generating Docker Compose or Terraform code from the map (can be a future phase, but out of scope for modeling).
- Strict enforcement of networking ports per container (handled in basic networking, not UML validation).

## Business Invariants

- The data model must support `parent_id` linking between regular devices to form an execution tree. Currently, `parent_id` is generic; it must recursively resolve to prevent circular dependencies.
- Validation logic matrix: 
  - `Location/Rack` > `Server/Switch/Router`
  - `Server` > `VM` | `LXC`
  - `VM` | `LXC` > `Docker/Container`
  - `Docker/Container` | `VM` | `Server` > `Service`
- Bypassing the canvas API to force a cyclic or invalid parent relationship at the database layer must be rejected by the domain layer.

## UX Interaction Spec

- **Visual Design**: The container borders should use solid lines for physical boundaries (Servers) and dashed/dotted lines for virtual boundaries (VMs/Docker), reflecting standard documentation practices.
- **Layer Toggle Widget**: A new floating FAB (Floating Action Button) in the top-right corner of the canvas (below the header). Click to open a checklist of execution layers: [x] Physical, [x] Virtual, [x] Containerized, [x] Services.
- **Feedback**: When dragging a node, the target container should highlight green if the drop is valid according to the matrix, or red if it violates execution bounds.

## Notes for Architect / Engineer

- **Database / Domain Models**: Ensure `DeviceType` Enum covers all required execution environments. The adjacency list (`parent_id`) must have a safety check in `src/domain/device_rules.py` checking the allowed `(child.type, parent.type)` pairs.
- **Cytoscape Rendering**: `canvas_js_utils.py` should inspect the node's `device_type` and output the appropriate `border-style` (`solid`, `dashed`) and `background-opacity`.
- **Layer Filtering**: Cytoscape handles filtering easily via `cy.nodes('[layer = "virtual"]').hide()`. You'll need to assign a `layer` tag to device types before sending them to the Cytoscape JSON payload in `topology_data.py`.
