# HT-020: Search and Filter Inventory

**Status:** Ready
**MoSCoW:** Must
**Kano:** Performance — the faster search returns results, the more the user trusts the inventory as their source of truth.
**Phase:** 1 (Hometower)
**Size:** M (3-4 days)

## Job-to-be-Done
As a homelab owner with 50+ devices, I want to search across all device fields using structured queries so that I can find exactly what I need without scrolling through a table.

## Context
HT-009 provides a basic inventory list with substring search on name/IP/notes and chip-based type/tag filtering. This story adds **structured search operators** that let power users write queries like `type:server ip:192.168.1.* tag:production` — the kind of search that makes Hometower competitive with Netbox for discoverability.

The search runs server-side to support future pagination at scale. Results render in the same inventory table (HT-009).

## Acceptance Criteria
- Given I type `type:server` in the search bar, when the query runs, then only devices with type=Server are shown
- Given I type `ip:192.168.1.*`, when the query runs, then devices whose IP matches the wildcard pattern are shown (glob-style, not regex)
- Given I type `tag:production`, when the query runs, then devices carrying a tag named "production" (case-insensitive) are shown
- Given I type `os:ubuntu`, when the query runs, then devices whose OS field contains "ubuntu" (substring, case-insensitive) are shown
- Given I type `location:rack-01`, when the query runs, then devices at a location whose name contains "rack-01" are shown
- Given I type `network:management`, when the query runs, then devices that belong to a network named "management" are shown (depends on HT-022)
- Given I type `service:plex`, when the query runs, then devices that run a service named "plex" are shown (depends on HT-023)
- Given I type `parent:proxmox`, when the query runs, then devices whose parent device name contains "proxmox" are shown (depends on HT-021)
- Given I combine operators `type:server tag:production`, when the query runs, then devices matching ALL operators (AND) are shown
- Given I type free text without an operator (e.g., `proxmox`), when the query runs, then it searches across name, IP, OS, notes, and location name (same as HT-009 basic search)
- Given I type an invalid operator (e.g., `foo:bar`), when the query runs, then it treats the entire string as free text (graceful fallback, no error)
- Given I `GET /api/devices?q=type:server+tag:production`, when the API processes it, then the same structured search runs server-side and returns filtered results
- Given the search returns zero results, when the UI renders, then it shows "No devices match — try a different query" with a "Clear" button

## Non-Goals (explicitly out of scope)
- Full-text search index (pg_trgm, ElasticSearch) — v1 uses ILIKE and simple SQL
- Regex support in search patterns (glob `*` only)
- Saved searches / search history
- Search across connections, diagrams, or locations as top-level results (device-centric only)
- Custom field search (`field:serial=ABC123`) — Phase 2
- Boolean OR between operators (v1 is AND-only across operators)

## Open Questions
None — operator syntax, AND semantics, and free-text fallback are confirmed.

## Notes for Architect / Engineer
- Domain: `src/domain/search.py` — pure function `parse_query(raw: str) -> ParsedQuery` that extracts operators and free-text remainder. `ParsedQuery` is a dataclass with optional fields for each operator. Fully unit-testable.
- Repository: extend `device_repository.get_all()` with a `search: ParsedQuery` parameter that builds dynamic SQLAlchemy filter clauses
- Wildcard `*` maps to SQL `LIKE` with `%` replacement — sanitize to prevent SQL injection (escape `%` and `_` in user input, then replace `*` with `%`)
- Router: extend `GET /api/devices` with a `q` query parameter; if present, parse and filter server-side
- UI: the HT-009 search bar gains a structured-search mode — as the user types an operator prefix (e.g., `type:`), show an autocomplete dropdown with valid values
- Operators are additive: each narrows the result set (AND). Multiple values for the same operator are OR (e.g., `type:server type:vm` shows servers AND VMs)
- Performance: with <500 devices and simple ILIKE queries, no index optimization needed in v1
- File: `src/domain/search.py` (~80 lines), extensions to `src/repositories/device_repository.py` and `src/api/routers/devices.py`
