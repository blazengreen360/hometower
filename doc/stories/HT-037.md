# HT-037: Connection Port / Interface Mapping

**Status:** Ready
**MoSCoW:** Could
**Kano:** Performance — "which port is that on?" is the physical-layer question every homelabber asks when patching cables. Without it, the diagram is logically correct but physically useless for troubleshooting at the rack.
**Phase:** 1 (Hometower)
**Size:** S (1–2 days)

## Job-to-be-Done
As a homelab owner physically tracing cables, I want each connection to record which port/interface it plugs into on both ends so that my topology diagram tells me "Switch port 24 → Server eth0" instead of just "Switch → Server."

## Context
HT-004 built the Connection model with `source_id`, `target_id`, `type`, and `label`. HT-030 adds UI editing for those fields. But there's no concept of **which physical or logical interface** each end connects to. In reality:
- A 24-port switch has port 1–24
- A server has eth0, eth1, bond0, IPMI
- A NAS has LAN1, LAN2
- A router has WAN, LAN1–4

"Switch → Server" is incomplete. "Switch:24 → Server:eth0" is actionable. This story adds optional `source_port` and `target_port` text fields to the Connection model.

## Acceptance Criteria

### Data model
- Given the Connection model, when I inspect it, then it has two new optional string fields: `source_port` (max 64 chars) and `target_port` (max 64 chars)
- Given I `POST /api/connections` with `{source_id, target_id, type: "Ethernet", source_port: "24", target_port: "eth0"}`, then the connection is created with port data
- Given I `PATCH /api/connections/{id}` with `{source_port: "25"}`, then only the source port is updated
- Given I omit `source_port` and `target_port`, when the connection is created, then both default to null (backward compatible)

### Canvas display
- Given a connection has port data, when the edge renders on the canvas, then the edge label shows: "{label} ({source_port} → {target_port})" — e.g. "Ethernet (24 → eth0)"
- Given only one port is set (e.g. source_port only), when the label renders, then it shows the available port only: "Ethernet (24 →)"
- Given neither port is set, when the label renders, then it shows only the label or type (same as today)

### Detail panel
- Given I click an edge and the connection detail panel opens (HT-030), when I see the form, then there are two additional text fields: "Source Port" (placeholder: "e.g. eth0, port 24") and "Target Port"
- Given I edit a port field and save, when the save completes, then the edge label on the canvas updates immediately

### Inventory cross-reference
- Given I view a device's detail panel (HT-010) connections section, when connections are listed, then each connection row shows the port on this device's end (e.g. "eth0 → Switch:24")

## Non-Goals (explicitly out of scope)
- Port number validation against a device's known port count (no device model for "this switch has 24 ports")
- Port status tracking (up/down/speed/duplex)
- Auto-detection of port assignments (LLDP, CDP) — Phase 2
- Predefined port templates per device type
- Port diagram or physical port layout visualization

## Open Questions
None.

## Notes for Architect / Engineer
- **Migration**: Alembic migration adding `source_port VARCHAR(64) NULL` and `target_port VARCHAR(64) NULL` to the `connections` table.
- **Model changes**: Add `source_port` and `target_port` to `ConnectionBase`, `ConnectionCreate`, `ConnectionUpdate`, and `ConnectionResponse` in `src/models/connection.py`.
- **Edge label JS**: Update the Cytoscape edge label builder in `canvas.py` to include port info when present. Format: `{label} ({source_port} → {target_port})` — keep it concise for canvas readability.
- **Backward compatible**: Existing connections with null ports continue to work unchanged. No data migration needed beyond the column addition.
