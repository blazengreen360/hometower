# HT-039: Device Status Field

**Status:** Ready
**MoSCoW:** Should
**Kano:** Performance — every inventory tool has this (NetBox: Active/Planned/Staged/Failed/Decommissioned; Homebox: similar). More status granularity = more useful inventory. Its absence makes Hometower feel incomplete next to alternatives.
**Phase:** 1 (Hometower)
**Size:** S (1 day)

## Job-to-be-Done
As a homelab owner, I want to mark each device with a status (Active, Offline, Maintenance, Planned, Decommissioned) so that I can see at a glance which parts of my infrastructure are running, down for maintenance, or retired.

## Context
The Device model currently has `name`, `type`, `ip`, `mac`, `os`, `notes`, `location_id`. There is no status field. All devices are implicitly "active" — there's no way to distinguish a running server from one that's powered off for upgrades or a decommissioned box sitting on a shelf.

NetBox has a rich lifecycle: Active → Planned → Staged → Failed → Inventory → Decommissioned → Offline. For a homelab tool, a simpler set is appropriate.

### Proposed enum: `DeviceStatus`
| Value | Meaning | Canvas visual |
|---|---|---|
| `Active` | Running and operational (default) | Normal node appearance |
| `Offline` | Powered off intentionally | Dimmed opacity (0.5) |
| `Maintenance` | Temporarily down for work | Orange border / badge |
| `Planned` | Not yet deployed | Dashed border |
| `Decommissioned` | Retired, kept for records | Greyed out + strikethrough label |

## Acceptance Criteria

### Data model
- Given the migration runs, when I inspect the `devices` table, then a `status` column exists with type `VARCHAR` and default value `Active`
- Given I create a device without specifying status, when it is saved, then `status` = `Active`
- Given existing devices before the migration, when the migration runs, then all existing devices have `status` = `Active`

### API
- Given I `POST /api/devices` with `"status": "Maintenance"`, when the request is valid, then the device is created with that status
- Given I `PATCH /api/devices/{id}` with `"status": "Decommissioned"`, when the request succeeds, then the device's status is updated
- Given I send an invalid status value (e.g. `"status": "Broken"`), when the API validates, then it returns `422` with the valid options listed

### Device detail panel
- Given I open a device's detail panel (HT-010), when I view the fields, then Status is shown as a dropdown with all 5 values
- Given I am a Contributor or Admin, when I change the status dropdown, then I can save the update
- Given I am a Reader, when I view the status, then it displays as read-only text

### Inventory list
- Given I view the inventory table (HT-009), when the table renders, then a "Status" column is visible with a coloured badge (green=Active, grey=Offline, orange=Maintenance, blue=Planned, red=Decommissioned)
- Given the inventory has devices with different statuses, when I use column filters (HT-020 or existing), then I can filter by status

### Canvas visual
- Given a device has status `Offline`, when it renders on the topology canvas, then the node opacity is reduced to 0.5
- Given a device has status `Planned`, when it renders, then the node border is dashed
- Given a device has status `Decommissioned`, when it renders, then the node is greyed out

## Non-Goals (explicitly out of scope)
- Automatic status detection (ping, SNMP) — that's Phase 2 auto-discovery
- Status history / changelog — that's the Phase 2 audit log
- Uptime tracking or status alerts
- Custom user-defined statuses
