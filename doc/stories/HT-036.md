# HT-036: Unified Toast / Notification System

**Status:** Ready
**MoSCoW:** Must
**Kano:** Basic — without consistent feedback, users don't know if their actions succeeded. Silence after a save/delete/error breeds distrust. Every modern web app has toasts; their absence signals "unfinished."
**Phase:** 1 (Hometower)
**Size:** S (1 day)

## Job-to-be-Done
As a Hometower user, I want clear, consistent visual feedback after every action (save, delete, error, warning) so that I always know whether my operation succeeded or failed without hunting for clues.

## Context
Hometower currently has no standardised feedback mechanism. Some pages use inline error labels, others silently succeed. HT-025 mentions a "success toast" but no toast component exists. HT-027 (design system) references toast entrance/exit animations but has no story to build the component itself.

This story creates a reusable toast component that all pages and components use for action feedback. It must be built **before or alongside** HT-026 (app shell) since the shell is the ideal host for the toast container.

### Toast types
| Type | Icon | Color token | Use case |
|---|---|---|---|
| Success | `check_circle` | `success` | Save completed, device created, tag added |
| Error | `error` | `error` | API failure, validation error, network timeout |
| Warning | `warning` | `warning` | Partial success, unsaved changes |
| Info | `info` | `accent` | Neutral notification, clipboard copied |

## Acceptance Criteria

### Display
- Given an action triggers a toast, when the toast appears, then it slides in from the top-right corner of the viewport with a 200ms ease animation
- Given a toast is visible, when 4 seconds elapse (default duration), then it automatically fades out (300ms ease) and is removed from the DOM
- Given a toast is visible, when I click the X (close) button on the toast, then it dismisses immediately with a fade-out
- Given a toast is visible, when I hover over it, then the auto-dismiss timer pauses — it resumes when I move the mouse away
- Given multiple toasts fire in rapid succession, when they render, then they stack vertically (newest on top) with 8px gap, up to a maximum of 5 visible toasts — the 6th toast pushes out the oldest

### Content
- Given a success toast fires, when I read it, then it shows a green `check_circle` icon, bold title (e.g. "Device saved"), and optional description text
- Given an error toast fires, when I read it, then it shows a red `error` icon, bold title (e.g. "Save failed"), and the error detail from the API response
- Given a toast has a long description, when it renders, then the description is truncated to 2 lines with ellipsis — hovering shows the full text in a tooltip

### API / Developer interface
- Given an engineer wants to show a toast, when they call `show_toast(type="success", title="Device saved", description="pihole updated")` from any NiceGUI page or component, then the toast appears — no need to import a specific page's UI container
- Given the toast system is initialized, when the app shell renders, then a toast container `<div>` is injected into the page body at a fixed position (top-right, z-index above modals)

### Accessibility
- Given a toast appears, when a screen reader is active, then the toast content is announced via `role="alert"` and `aria-live="polite"`
- Given a toast has a close button, when I Tab to it, then it is focusable and activatable with Enter/Space

### Theme awareness
- Given the active theme is Dark, when a toast renders, then it uses the Dark theme's surface and text tokens (from HT-027). Before HT-027 ships, use the existing `COLOR_SURFACE_ALT` and `COLOR_TEXT` from `tokens.py`

## Non-Goals (explicitly out of scope)
- Persistent notification center / notification history
- Toast actions (e.g. "Undo" button inside the toast) — v1 toasts are informational only
- Toast sounds or vibration
- Server-sent toasts (WebSocket push) — toasts are triggered by client-side action outcomes only
- Toast positioning options (always top-right)

## Open Questions
None.

## Notes for Architect / Engineer
- **Component**: `src/ui/components/toast.py` exporting `show_toast(type, title, description?, duration_ms?)`.
- **Implementation pattern**: NiceGUI's `ui.notify()` provides basic notification support. Evaluate whether it meets the stacking, animation, and styling requirements. If not, implement a custom toast container via `ui.add_body_html()` with a small JS manager for animations and stacking.
- **Global access**: Use NiceGUI's `app.storage` or a module-level reference so any component can call `show_toast()` without needing a reference to a specific UI element.
- **Integration**: After this story ships, retrofit existing pages that have inline success/error messages to use `show_toast()` instead. This can be done incrementally — not all at once.
- **Z-index**: Toasts must render above modals (z-index > 9999) and the sidebar.
