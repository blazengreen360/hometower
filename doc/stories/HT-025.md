# HT-025: Self-Service Password Change + First-Boot Credential Hardening

**Status:** Ready
**MoSCoW:** Must
**Kano:** Basic — users expect to change their own password without asking an admin, and operators expect a seed credential to stop being a backdoor after it has done its job.
**Phase:** 1 (Hometower)
**Size:** S (1–2 days)

## Job-to-be-Done
As any authenticated user, I want to change my own password from inside the app so that I am not forever bound to the credential that was handed to me (or set in `.env` on first boot).

As an operator, I want the `ADMIN_PASSWORD` seed value in `.env` to stop being a valid login credential after the first admin has been created so that anyone with read access to `.env` cannot hijack the admin account after the admin has rotated their password.

## Context
HT-001 seeds the first admin from `ADMIN_EMAIL` + `ADMIN_PASSWORD` in `.env` on first boot via `create_first_admin_if_needed()` in `src/services/auth_service.py`. HT-019 (not yet shipped) will give admins the ability to reset *other* users' passwords from the Admin User Panel.

What is still missing:

1. **Self-service password change.** Today, a user who wants to rotate their own password has no path at all. The only password-related endpoint is `POST /api/auth/login`. HT-019 explicitly lists self-service profile editing as a Non-Goal (`doc/stories/HT-019.md:29`), so a dedicated story is required.
2. **First-boot credential invalidation.** `create_first_admin_if_needed()` only runs when the users table is empty, which is already correct — but nothing warns the operator that leaving `ADMIN_PASSWORD` in `.env` forever is pointless and noisy. Worse, the current Context framing in HT-017 implied that `.env` was the recovery path, which it should not be after a password change has happened in the DB.

After this story ships, HT-017's CLI `reset-password` tool becomes the narrow last-resort recovery path for the rare scenario where the only Admin has forgotten their password AND no other Admin exists to reset them via HT-019.

## Acceptance Criteria

### Self-service password change

- Given I am logged in, when I open the user menu and click **Change Password** (or navigate to `/settings/profile`), then I see a form with three fields: **Current Password**, **New Password**, **Confirm New Password**
- Given I submit the form with a valid current password and matching new/confirm values, when `PATCH /api/auth/me/password` returns 204, then my `password_hash` is updated in the database, my existing JWT remains valid until its natural expiry, and I see a success toast: "Password updated"
- Given I submit the form with an incorrect current password, when the API responds, then I receive HTTP 401 with detail `"Current password is incorrect"` and the stored hash is unchanged
- Given I submit the form with a new password shorter than 8 characters, when the API validates, then I receive HTTP 422 with detail `"Password must be at least 8 characters"` (same wording as HT-017 and HT-019 for consistency)
- Given I submit the form where **New Password** and **Confirm New Password** do not match, when the frontend validates before submit, then I see an inline error `"Passwords do not match"` and no request is sent to the API
- Given I submit the form with the new password equal to the current password, when the API validates, then I receive HTTP 422 with detail `"New password must be different from current password"`
- Given the password change succeeds, when the success handler runs, then a Loguru `info` event is emitted: `Password changed for user_id={}` with **no password material** in the log (not plaintext, not hash)
- Given I am unauthenticated, when I call `PATCH /api/auth/me/password` directly, then I receive HTTP 401 from the auth middleware before the handler runs

### First-boot credential hardening

- Given the users table already contains at least one user, when the application boots, then `create_first_admin_if_needed()` is a no-op (unchanged — already correct today)
- Given the users table already contains at least one user AND `settings.admin_password` is still set to a non-empty value, when the application boots, then a Loguru `warning` is emitted exactly once per boot: `ADMIN_PASSWORD is set in .env but first-boot seeding has already run; this value is ignored. Remove it from .env to silence this warning.`
- Given I change the admin's password via the self-service form, when I then restart the container without touching `.env`, then logging in with the original `ADMIN_PASSWORD` value fails with 401 (the DB hash is authoritative — the `.env` value is never compared against it anywhere except first-boot seeding)
- Given I read `.env.example`, when I look at the `ADMIN_PASSWORD` line, then I see the comment: `# Used ONLY on first boot to seed the initial admin. After first boot, change your password in Settings → Profile and remove this line.`

## Non-Goals (explicitly out of scope)
- Password complexity rules beyond minimum length (no required uppercase, symbols, digits) — intentional for homelab ergonomics
- Two-factor authentication / TOTP — Phase 2
- Password history / preventing reuse of the last N passwords — Phase 2
- Email verification or notification on password change (no email system in Phase 1)
- Forced password rotation on first login after seed — consider for a later hardening story
- Automatic mutation of the operator's `.env` file on disk — the app never writes to `.env`; it only logs a warning and ignores the value
- Session invalidation on password change — existing JWTs continue to work until their natural expiry. A separate story can add "revoke all sessions" if required
- Admin-resets-other-user password flow — **already covered by HT-019** (`doc/stories/HT-019.md:20`), do not duplicate here

## Open Questions
None — scope is bounded to one self-service endpoint, one new UI page, and a runtime-level invalidation of the seed credential.

## Notes for Architect / Engineer

### New shared domain helper (eliminates duplication across HT-017, HT-019, HT-025)
- Create `src/domain/auth.py` with a pure function `validate_password_strength(password: str) -> None` that raises `ValueError("Password must be at least 8 characters")` when `len(password) < 8`
- Refactor HT-017's CLI check and HT-019's admin-reset check to call this helper. Today the check is duplicated; keeping three sources of truth for a password rule is exactly the kind of drift Code-Reviewer should flag
- No dependencies beyond stdlib — `src/domain/` rules (pure Python, no I/O)

### API endpoint
- New handler in `src/api/routers/auth.py`: `PATCH /api/auth/me/password`
- Request body (Pydantic): `{current_password: str, new_password: str}` — no `confirm_new_password` at the API level (that's a frontend concern)
- Extract the caller's user_id from the JWT (via the existing auth middleware / `Depends`)
- Delegates to a new service function

### Service layer
- New function in `src/services/auth_service.py`: `change_own_password(user_id: UUID, current: str, new: str, session: Session) -> None`
- Steps:
  1. `user_repository.get_by_id(session, user_id)` — 404 if missing (should not happen if JWT is valid, but guard anyway)
  2. `verify_password(current, user.password_hash)` — raise `HTTPException(401, "Current password is incorrect")` on mismatch
  3. `locations_domain`-style call into `src/domain/auth.py::validate_password_strength(new)` — translate `ValueError` → `HTTPException(422, ...)`
  4. Reject if `new == current` — raise `HTTPException(422, "New password must be different from current password")`
  5. `user.password_hash = hash_password(new)`; `user.updated_at = datetime.now(timezone.utc)`; `user_repository.update(session, user)`
  6. `logger.info("Password changed for user_id={}", user_id)` — never log the plaintext or hash

### Repository layer
- `src/repositories/user_repository.py` already has `update()` — no new method needed

### UI
- New page: `src/ui/pages/settings_profile.py` at route `/settings/profile`
- Simple NiceGUI form: three `ui.input(..., password=True)` fields, a Save button, an error label
- Frontend validation: `new == confirm` before submit (fast feedback); backend returns the authoritative error on the rest
- Add a **Change Password** item to the top-nav user menu (wherever the logout button currently lives). Check `src/ui/` for the nav component — reuse, don't fork
- Match existing design tokens in `src/ui/design/tokens.py` — no hardcoded colors

### First-boot credential hardening
- Modify `create_first_admin_if_needed()` in `src/services/auth_service.py`:
  - Keep the existing `if user_repository.count(session) == 0:` branch **exactly as-is**
  - Add an `else:` branch: `if settings.admin_password: logger.warning("ADMIN_PASSWORD is set in .env but first-boot seeding has already run; this value is ignored. Remove it from .env to silence this warning.")`
- Verify nothing else in the codebase reads `settings.admin_password` after first boot (`grep -rn "admin_password" src/` should return only `settings.py`, first-boot seeder, and the new warning branch)
- Update `.env.example` with the comment specified in the AC above

### Tests

- **Unit, service**: `tests/unit/test_auth_service.py::test_change_own_password_*` — happy path, wrong current password, short new password, new-equals-current, user-not-found
- **Integration**: `tests/integration/test_auth_api.py::test_patch_me_password_*` — full HTTP flow with a real test DB, including the 401 for unauthenticated requests
- **Integration**: `tests/integration/test_first_boot_seed.py` — boot with empty users table + `ADMIN_PASSWORD` set → admin created, no warning. Boot with populated users table + `ADMIN_PASSWORD` set → no seed, warning logged. Boot with populated users table + `ADMIN_PASSWORD` unset → no seed, no warning
