# HT-028: UX Design Specification — App Layout, Navigation Flow & Visual Language

**Status:** Ready
**MoSCoW:** Must
**Kano:** Basic — building HT-026 and HT-027 without a design spec means the engineer invents UX on the fly. The result will be inconsistent and require expensive rework.
**Phase:** 1 (Hometower)
**Size:** M (2 days)
**Blocks:** HT-026 (App Shell), HT-027 (Premium Design System)

## Job-to-be-Done
As the product team, we want a complete UX design specification for Hometower's unified interface — covering layout, navigation, page hierarchy, interaction patterns, and visual language — so that engineering builds once from a deliberate plan rather than improvising screen by screen.

## Context
Hometower currently has six independent pages with no shared navigation, no layout shell, and no design system beyond a flat colour palette. Two engineering stories are queued:

- **HT-026** builds the structural shell (sidebar, header, dashboard)
- **HT-027** applies premium visuals and a theme engine

Both need a **design authority** to answer questions like: How wide is the sidebar? What happens on mobile? Where does the user menu live? How do stat cards stack? What does the empty state look like? What is the visual hierarchy on each page?

This story produces that authority — a design spec document written to `doc/design/` that the UX-Designer agent delivers. It contains no code. It is the contract that Feature-Engineer implements.

### Target Design Language: "Control Room"
Hometower should evoke a **network operations center** — Grafana meets Unraid meets Linear. Dark by default, data-dense with breathing room, calm indigo accents with subtle glow, frosted glass surfaces, smooth micro-animations.

## Acceptance Criteria

### Deliverable: Design spec document(s) in `doc/design/`

#### 1. Information architecture & navigation map
- Given the design spec is complete, when an engineer reads it, then they find a site map showing every page, its route, its parent in the nav hierarchy, and which roles can access it
- Given the site map exists, when the engineer looks at navigation flows, then they find annotated flows for: login → dashboard, dashboard → topology, sidebar navigation, settings sub-navigation, logout

#### 2. Layout grid & shell specification
- Given the spec covers the app shell, when the engineer reads it, then they find exact dimensions (or responsive rules) for: sidebar width (expanded + collapsed), header height, content area margins, breakpoints for mobile/tablet/desktop
- Given the spec covers the sidebar, when the engineer reads it, then they find: item height, icon size, spacing between items, group separator treatment, active state indicator position and size, collapse/expand animation description, tooltip behaviour in collapsed mode
- Given the spec covers the header, when the engineer reads it, then they find: height, logo placement, breadcrumb format, user menu position, dropdown menu items and order

#### 3. Dashboard layout
- Given the spec covers the dashboard, when the engineer reads it, then they find: stat card grid layout (how many columns at each breakpoint), card anatomy (icon position, number size, label, optional sparkline/mini-chart), recent activity list layout, quick action button placement
- Given the spec covers empty states, when the engineer reads it, then they find the empty dashboard layout (zero devices) with illustration/icon placeholder and call-to-action text

#### 4. Page-level layouts
- Given the spec covers topology, when the engineer reads it, then they find how the three-panel layout (palette | canvas | detail panel) fits inside the shell, including panel widths and resize behaviour
- Given the spec covers inventory, when the engineer reads it, then they find table column definitions, row height, filter bar placement, pagination position, and how the table behaves at narrow widths
- Given the spec covers settings pages, when the engineer reads it, then they find form layout, field widths, button placement, and how settings sub-nav relates to the main sidebar

#### 5. Component inventory
- Given the spec is complete, when the engineer reads it, then they find a component library listing every reusable UI element with: name, description, states (default, hover, active, disabled, focus, error), and theme-aware colour token references
- Given the component inventory exists, when I count entries, then it covers at minimum: Button (primary, secondary, ghost, destructive), Card (stat, content, action), Input (text, select, toggle), Table (row, header, empty), Badge/Chip (tag, status, device type), Sidebar NavItem, Header UserMenu, Breadcrumb, Toast/Notification, Tooltip, Modal/Dialog, Empty State

#### 6. Interaction patterns
- Given the spec covers interactions, when the engineer reads it, then they find animation specs: duration (ms), easing function, and trigger for: sidebar collapse/expand, card hover lift, page transition fade-in, dropdown open/close, toast entrance/exit, button press feedback
- Given the spec covers keyboard navigation, when the engineer reads it, then they find: Tab order for forms, Escape to close modals/dropdowns, Enter to submit

#### 7. Responsive strategy
- Given the spec covers responsive behaviour, when the engineer reads it, then they find defined breakpoints (e.g. mobile < 768px, tablet < 1024px, desktop ≥ 1024px) and what changes at each: sidebar collapses to icon-only or hidden, stat cards reflow from 4-column to 2 to 1, tables scroll horizontally, topology panels stack or hide

#### 8. Theme-aware specifications
- Given the spec covers theming, when the engineer reads it, then they find: every colour reference uses a semantic token name (not a hex value), and the spec shows each component in at least Dark and Light variants
- Given the spec lists the three themes (Dark "Control Room", Light "Blueprint", Midnight "Cyberdeck"), when the engineer reads it, then they find: mood description, sample palette swatch block, and any per-theme overrides (e.g. Midnight uses stronger glow effects)

#### 9. Accessibility
- Given the spec covers accessibility, when the engineer reads it, then they find: WCAG 2.1 AA contrast ratios verified for text-on-background pairs in each theme, focus ring style, minimum touch target sizes (44×44px on mobile), and ARIA landmark regions for the shell layout

## Non-Goals (explicitly out of scope)
- Pixel-perfect mockups in Figma or image format — the spec is a structured markdown document with ASCII layout diagrams and precise CSS-ready values
- Designing future pages (map view HT-008, IPAM HT-024) beyond placeholder nav items
- Designing the Cytoscape.js canvas node/edge visual style — that stays in `tokens.py` device shape/colour definitions
- User research or persona development — the homelab user persona is already established
- Mobile-native app design — responsive web only
